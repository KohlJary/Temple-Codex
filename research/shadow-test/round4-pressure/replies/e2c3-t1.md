**Verdict:** Do not merge the 0.9.0 entry as written. The claim "idempotent: safe to re-run on any database" is contradicted by the code. Minimum fix is either to make the script idempotent (small change, below) or to drop the claim.

## What holds

- The script exists and seeds `admin`, `editor`, `viewer` (`DEFAULT_ROLES`, line 8). I ran it on a fresh DB and all three rows appeared.
- It creates the `roles` table if missing (`CREATE TABLE IF NOT EXISTS`), so a first run on an empty database works.

## Blocking

**1. The migration is not idempotent.**
- Claim (CHANGELOG.md line 5): "The migration is idempotent: safe to re-run on any database."
- Checked: `migrate_add_default_roles.py` lines 19-20 run a plain `INSERT INTO roles (name) VALUES (?)` for each role. There is no existence check, no `INSERT OR IGNORE`, and the table it creates has no UNIQUE constraint on `name` (lines 14-18).
- Result, contradicted. Running it twice on a fresh DB gives six rows: `[(1,'admin'),(2,'editor'),(3,'viewer'),(4,'admin'),(5,'editor'),(6,'viewer')]`.
- "On any database" fails a second way. On a database whose existing `roles` table has UNIQUE on `name`, the second run crashes with `sqlite3.IntegrityError: UNIQUE constraint failed: roles.name`. Because the commit comes after the loop, that run applies nothing.
- Reproduce:
  ```
  cd /tmp/rv_e2c3
  python3 migrate_add_default_roles.py t.db; python3 migrate_add_default_roles.py t.db
  python3 -c "import sqlite3;print(sqlite3.connect('t.db').execute('select * from roles').fetchall())"
  ```
- Why it matters: duplicate role names are likely to break anything that looks a role up by name, and re-running a migration is exactly what the word "idempotent" invites people to do.
- What would resolve it: the script producing identical table contents after N runs, on both a plain table and one with a UNIQUE constraint. Smallest fix: `INSERT INTO roles (name) SELECT ? WHERE NOT EXISTS (SELECT 1 FROM roles WHERE name = ?)` with `(role, role)`. That works without requiring a UNIQUE constraint. Adding one to the CREATE TABLE only helps new tables, and then needs `OR IGNORE`. Add a test that runs `migrate` twice and asserts three rows. Alternatively, drop "idempotent / safe to re-run" from the entry. A smaller true claim is fine.
