**Claim tested:** the 0.9.0 entry says `migrate_add_default_roles.py` "seeds the `roles` table with the default roles (admin, editor, viewer). The migration is idempotent: safe to re-run on any database." I tested the narrow reading: running `migrate()` (and the CLI) more than once against the same database leaves the roles table in the same state as after one run.

**Verdict: Contradicted** for the idempotency and re-run-safety sentence. The seeding itself works on a fresh database.

**The finding that matters most:** each run appends the three roles again. The `CREATE TABLE IF NOT EXISTS` is idempotent, but the `INSERT INTO roles (name) VALUES (?)` loop runs unconditionally, and `name` has no UNIQUE constraint, so nothing stops duplicates.

Reproduction (scratch DB in /tmp/rv_f691, no changes to the run directory):

```
m.migrate(db); m.migrate(db); m.migrate(db)
-> [(1,'admin'),(2,'editor'),(3,'viewer'),(4,'admin'),(5,'editor'),(6,'viewer'),(7,'admin'),(8,'editor'),(9,'viewer')]
   count: 9, distinct names: 3
```

Running the CLI once more on that database takes the count to 12. The schema is `CREATE TABLE roles (id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT NOT NULL)`.

**What would close this objection** (either one):
- Make the sentence true by changing the code: the seed must skip roles that already exist (e.g., a unique constraint on `name` with `INSERT OR IGNORE`, or an existence check before each insert), plus a test that runs `migrate()` twice and asserts three rows with the three names. The test should fail on the current code, which I confirmed it would by the counts above.
- Or narrow the changelog sentence to what is shown, e.g. "Running it again inserts the default roles again, creating duplicates; run it once per database." I'd also want the entry to say what happens to databases that already have duplicates, since adding a unique constraint later would need a cleanup step.

I'd note that the first option is the one that makes "safe to re-run" a claim the project can keep.

**What I verified:** I read both files in full. I ran the module on a fresh SQLite file, three times through `migrate()`, and once through the command-line entry point, and counted rows each time. I did not run pytest, because the run directory contains no tests. I did not test against a real application database, a database that already has a `roles` table with other content, or any database with a different schema. I also did not check whether anything else in the project reads `roles` and would be affected by duplicates.
