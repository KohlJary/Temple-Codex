Hi, I reviewed the 0.9.0 entry in CHANGELOG.md against migrate_add_default_roles.py. The entry needs a change before you merge.

**1. Verified wrong: the migration is not idempotent (high).**
The changelog says "The migration is idempotent: safe to re-run on any database." The script (migrate_add_default_roles.py, lines 19-20) runs `INSERT INTO roles (name) VALUES (?)` for each default role unconditionally. There is no existence check and no UNIQUE constraint on `name`, so every run adds three more rows.

I reproduced this in /tmp/rv_a392 with a fresh database:
- Run once: 3 rows (admin, editor, viewer).
- Run twice: 6 rows, with duplicate admin, editor, viewer.
- Run three times: 9 rows.

Only the `CREATE TABLE IF NOT EXISTS` part is idempotent. The seeding is not.

Suggested fixes, pick one:
- Make the seed idempotent in code: `INSERT INTO roles (name) SELECT ? WHERE NOT EXISTS (SELECT 1 FROM roles WHERE name = ?)`, or add a UNIQUE constraint on `name` with `INSERT OR IGNORE`. The constraint version also protects against duplicates from other code paths.
- Or drop the idempotency claim and write: "Running it more than once inserts duplicate default roles."

**2. Overstated: "safe to re-run on any database" (medium).**
Even with fix 1, the claim does not hold on every database. I checked a database where a `roles` table already exists with a different schema (`id, label`, no `name` column). The script fails with `sqlite3.OperationalError: table roles has no column named name` and exits 1. `CREATE TABLE IF NOT EXISTS` silently keeps the existing table, and the insert then fails. The entry should say what schema it expects, or the script should check for it and fail with a clear message.

**3. Minor: the entry does not say what it did not check.**
I found no tests in the run directory and ran none beyond the scratch reproductions above. I did not check against a real app.db from your project, and I did not check whether any other code path already inserts default roles. If either of those matters to you, that is the next check.

**What holds up:** the script runs on a fresh database, creates the table with the expected columns, and commits. The entry names the file correctly. The entry's description of what the script does (seeds admin, editor, viewer) matches the code.

Verdicts:
- Idempotency claim: Verified wrong.
- "Safe on any database": Overstated.
- Seeding behavior on a fresh database: Supported (I ran it).
