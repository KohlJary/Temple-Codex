Yes, I'm sure about the duplication, and I'm not sure about the Friday impact. Those are two different claims, and the changelog makes the first one.

What I ran: a copy of migrate_add_default_roles.py in /tmp/rv_a957, run three times against one scratch database. After the three runs the roles table held nine rows: admin, editor and viewer, three times each. The script's line 20 inserts every role on every run, and name has no UNIQUE constraint, so nothing stops the repeat. The rerun is the reproduction. You can see it in the output I posted in the review.

Why "nothing broke" doesn't settle it: the changelog says "idempotent: safe to re-run on any database." That is a claim about the data, not about whether a demo fails. Staging may have run the migration twice and shown no error, because nothing in the demo reads roles by name, or because it only ever ran on an empty table. Both are consistent with a duplicated table. Silence in a demo doesn't show the rows are unique.

The test that settles it, and it takes one query on staging:

    SELECT name, COUNT(*) FROM roles GROUP BY name;

If every role shows a count of 1, I withdraw the finding and the changelog line stands for staging. If any shows 2 or more, the claim is false for staging, and the demo may be reading duplicate rows even if it looks fine.

Two ways to ship before Friday, whichever you prefer:
(a) Keep the script and change the changelog line to "Seeds the roles table on a fresh database. Not safe to re-run on a database that already has these roles." This is true today.
(b) Guard the insert: `INSERT INTO roles (name) SELECT ? WHERE NOT EXISTS (SELECT 1 FROM roles WHERE name = ?)`. I tested this in scratch. Three runs on a fresh database gave three rows, and a run against the nine-row database added nothing. Then the idempotence claim is true as written. Note that it does not remove duplicates already in staging. If the query above shows duplicates, you'll need to delete the extra rows separately.

What I still haven't checked: the code that reads from the roles table, so I can't say whether duplicates would change any access decision. That's a gap, and reading the callers would close it.

Verdicts: the "roles table is seeded" claim stands as narrower, for a fresh database. The idempotence claim is unsupported as written.
