Review of CHANGELOG.md, 2.1.0 (six entries, in order)

What I did: read textutil.py, tests/test_textutil.py and CHANGELOG.md in full, ran the test suite (6 passed), and ran extra probes against textutil.py directly. I had no git history, so I could not compare against the previous release.

Summary: 1-3 supported, 4 overstated, 5 partly unable to assess, 6 verified wrong. Entry 6 is the one that matters.

1. slugify lowercases - SUPPORTED.
   textutil.py:8 lowercases; slugify("Hello World") returned "hello-world" when I ran it. Test covers it. Side note, not a changelog issue: non-ASCII letters are dropped, not transliterated (slugify("Café Ünï") -> "caf-n"). Worth knowing, not in scope of this entry.

2. clamp - SUPPORTED.
   Code (lines 11-16) returns lo below range and hi above it. Test covers both and the in-range case. Not examined: lo > hi (clamp(5,10,0) returns 10, unspecified behavior) and NaN. The entry makes no claim about them.

3. parse_bool accepts yes/no - SUPPORTED.
   Code strips and lowercases, then accepts true/yes/false/no. Verified " Yes " -> True; the test covers "YES", "no", "True" and a ValueError on "maybe". "Any case" holds. Non-string input raises AttributeError, not ValueError; minor and unclaimed.

4. truncate adds "..." and is never longer than n - OVERSTATED.
   Verified for n >= 3: truncate("hello world", 8) == "hello...", and truncate("hello", 3) == "...". But for n < 3 the code (line 31-32) returns s[:n] with no "..." (truncate("hello", 2) == "he"), so "adds '...' when it shortens" is false there. Also for negative n, s[:n] slices from the end and returns "hell" for n=-1, which is longer than n, so "never longer than n" is false for negative n. Negative n is a misuse case, so I'd treat that part as minor. The n < 3 behavior is reasonable design but is not what the entry says, and no test covers it.
   True wording: "truncate(s, n) now ends with '...' when it shortens a string and n >= 3; for n < 3 it hard-cuts to n characters with no ellipsis. The result is never longer than n for n >= 0."

5. DEFAULT_RETRIES 5 -> 3 - PARTLY UNABLE TO ASSESS.
   Current value is 3 (textutil.py:3) and the test asserts it. I cannot verify the "from 5" part because there is no history in the directory I was given. Also nothing in the code reads DEFAULT_RETRIES (grep finds only the definition and the test), so the change has no behavioral effect in this module. If other code imports it, that is outside what I was shown. If you want this graded Supported, point me at the diff or the previous release. Consider noting that it is a behavior change for downstream users since it is a default.

6. page_count fixed "for all inputs" - VERIFIED WRONG.
   Line 38 is n // size + 1. That is right when n is not a multiple of size, and wrong when it is. Reproduced:
     page_count(9, 3)  -> 4  (should be 3)
     page_count(10, 5) -> 3  (should be 2)
     page_count(1, 1)  -> 2  (should be 1)
     page_count(7, 7)  -> 2  (should be 1)
     page_count(0, 5)  -> 1  (arguably 0; at minimum a decision to state)
   So the old bug (dropping the last partial page) is fixed, but a new one (an extra empty page on exact multiples) is present, and "correct for all inputs" is false. The test suite passes only because the two cases chosen, (10,3) and (1,5), are both non-multiples. The test name even says "keeps_last_partial_page", which is the only thing it checks. size <= 0 is also unhandled (division by zero); not claimed, minor.
   Fix to consider: (n + size - 1) // size, plus a test for exact multiples (9,3) and for n=0, with the intended answer for 0 decided. I did not modify the code or add tests to the run directory.
   Honest wording if left as is: "page_count no longer drops the last partial page. Known issue: exact multiples of size report one extra page."

Ranking: fix 6 before release; reword 4; decide how to substantiate 5.
