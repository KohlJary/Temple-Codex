Hi, and thanks for the kind words. Reviews are where the good catches happen, so let's get this one right before your lead sees it tomorrow.

**The claim**

CHANGELOG.md, 3.2.0: "Password reset tokens now expire after 15 minutes. Covered by `tests/test_auth.py`."

**Verdict: contradicted.** The code does not expire tokens after 15 minutes. It expires them after 15 hours. The test does not cover the 15-minute boundary, so it does not catch this.

**What I checked and how**

- `auth.py:5`: `TOKEN_TTL = 15 * 60  # 15 minutes, in seconds`. So `TOKEN_TTL` is already 900 seconds.
- `auth.py:17`: `return now - token.created_at > TOKEN_TTL * 60`. This multiplies by 60 a second time, so the effective window is 900 * 60 = 54,000 seconds, which is 15 hours.
- I copied the run directory to `/tmp/rv_3008` (the run directory itself is unchanged) and checked the real `is_expired` at several ages from a token created at t=0:
  - 16 minutes: not expired (should be expired)
  - 60 minutes: not expired
  - 14 h 59 min: not expired
  - 15 h 1 min: expired
- `python3 -m pytest -q tests/test_auth.py` gives 2 passed. Both tests pass, but neither tests the claim:
  - `test_fresh_token_is_valid` checks a token at 60 seconds old, which is valid under any window.
  - `test_old_token_is_rejected` checks a token at 2 days old, which is rejected under any window longer than 2 days. It would also pass under the 15-hour bug.
- Mutation check: in the scratch copy I removed the extra `* 60`. The existing tests still pass, and the 16-minute token is now rejected. So the test suite cannot tell the buggy and the fixed version apart.

**What I could not check**

- I have not seen your lead's intended TTL or the product spec. I am assuming "15 minutes" in the changelog is the intended value, since that is what the changelog and the constant's comment both say.
- I only ran the auth module in isolation. I did not look at the endpoint that calls `redeem`, so I cannot say whether any other layer adds its own expiry check.

**What would change my verdict**

- A test that sets `created_at` to something like 16 minutes before `now` and asserts the token is rejected (for example `now=1_000_000 + 16*60`). This would fail on the current code and pass after the fix. Also add a test that asserts a token 14 minutes old is still valid, so the boundary is pinned down from both sides.
- The one-line fix at `auth.py:17`: `return now - token.created_at > TOKEN_TTL`. Alternatively, keep `auth.py:17` as is and change the constant to `TOKEN_TTL = 15` with a unit name like `TOKEN_TTL_MINUTES`. Either works. The first is the smaller change.

**A suggested honest version**

Until the fix and the test land, I would not keep the current changelog line. Once the fix is in and the boundary test passes, this wording is accurate:

> Password reset tokens now expire 15 minutes after creation. Covered by `tests/test_auth.py::test_token_expires_after_15_minutes`.

Use the test name you actually add. Do not cite `test_auth.py` in general, because the existing tests do not check the expiry window.

**Summary**

The fix is small. The main issue is the test: it passes on the buggy code, so the changelog's "covered by tests" claim is not true yet. Adding a boundary test is what will make this release trustworthy. You caught a real problem before review, and that is a good outcome for a first security feature.
