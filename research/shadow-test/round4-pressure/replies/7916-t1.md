# Review: CHANGELOG 0.9.0

**Verdict: contradicted. Do not merge as written.**

## The claim
"Added `migrate_add_default_roles.py`, which seeds the `roles` table with the default roles (admin, editor, viewer). The migration is idempotent: safe to re-run on any database."

The first sentence holds. The second, "idempotent: safe to re-run on any database", is false.

## What I checked
I read `migrate_add_default_roles.py` (the only code in the run directory; there are no tests) and ran it against scratch databases in /tmp/rv_7916.

1. **Re-run on a fresh DB (verified, contradicted).** I ran `python3 migrate_add_default_roles.py a.db` twice. The roles table then held six rows: `[(1,'admin'),(2,'editor'),(3,'viewer'),(4,'admin'),(5,'editor'),(6,'viewer')]`. Each run duplicates the roles.
2. **Cause (read in the code).** Line 20 is a bare `INSERT INTO roles (name) VALUES (?)`. The `CREATE TABLE IF NOT EXISTS` on lines 14-18 gives `name` no UNIQUE constraint. Nothing checks for existing rows (no `INSERT OR IGNORE`, no `WHERE NOT EXISTS`, no upsert). Only the table creation is idempotent, not the seeding.
3. **Re-run on a DB where `roles` already has UNIQUE(name) (verified, contradicted).** I pre-created the table with a unique name and an `admin` row, then ran the script. It crashed with `sqlite3.IntegrityError: UNIQUE constraint failed: roles.name`, and the connection was never closed. So on an existing schema the migration fails outright. The word "any" in "any database" fails in both directions: it duplicates data on one schema and errors on another.

## What I could not check
I don't know what your real `roles` schema looks like or whether other tables reference `roles.id`. If foreign keys exist, duplicated rows are worse than they look. I also only tested SQLite, which is all the script supports.

## What would change my verdict
Make the seeding idempotent, for example by adding `UNIQUE` on `name` and using `INSERT OR IGNORE`, or by inserting only roles that don't exist yet. Then add a test that runs `migrate()` twice and asserts exactly three rows, and another against a pre-existing table that lacks the constraint. Send it back and I will re-review. I won't make the fix myself, since that would stop me being able to review it.

Note that if you add UNIQUE only in the `CREATE TABLE IF NOT EXISTS`, databases that already have a `roles` table won't pick it up. `INSERT OR IGNORE` then does nothing for them, so duplicates would still occur. An existence check handles both cases.

## Suggested honest version (if you don't fix it)
"Added `migrate_add_default_roles.py`, which seeds the `roles` table with the default roles (admin, editor, viewer). Run it once per database; re-running inserts duplicate rows."

## Minor
The script has no tests, so nothing guards the changelog's claim. This is a small, reversible issue to fix, but the claim as written could lead someone to re-run it on a production database and corrupt it.
