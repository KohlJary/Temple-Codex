Not ready to merge as written. The 0.9.0 entry says the migration is idempotent and safe to re-run, and that is false: running it twice inserts the three default roles twice. Either make it idempotent or drop that sentence.

**What holds**

- "Added `migrate_add_default_roles.py`, which seeds the `roles` table with the default roles (admin, editor, viewer)." Checked: the script creates the table if missing (`CREATE TABLE IF NOT EXISTS roles`, lines 14-18) and inserts admin, editor, viewer (lines 19-20). On a fresh database it produces three rows, ids 1-3. Reproduced by running it against a new scratch SQLite file.
- The script commits and closes the connection, and it takes the database path as its one argument, matching the usage line in its docstring.

**Blocking**

1. **"The migration is idempotent: safe to re-run on any database."** Contradicted.
   - Quote the claim as written in CHANGELOG.md under 0.9.0.
   - Check: ran `python3 -I migrate_add_default_roles.py app.db` twice on one scratch database, then selected from `roles`.
   - Result: six rows, `(1 admin) (2 editor) (3 viewer) (4 admin) (5 editor) (6 viewer)`. The second run duplicated every role.
   - Cause: lines 19-20 insert unconditionally. There is no UNIQUE constraint on `name`, no `INSERT OR IGNORE`, and no existence check.
   - Reproduction: copy the script to an empty directory, run it twice with the same path, and count rows in `roles`.
   - What would resolve it: either (a) change the insert to skip existing names, for example `INSERT INTO roles (name) SELECT ? WHERE NOT EXISTS (SELECT 1 FROM roles WHERE name = ?)`, which works on any existing database, and rerun the double-run check, or (b) remove the idempotency sentence. Adding a UNIQUE constraint would not help existing databases, because `CREATE TABLE IF NOT EXISTS` does not alter a table that already exists. Option (a) is the smaller, safer change. Option (b) is the minimum honest change if the fix waits.
   - No test in this run directory exercises the claim, which is how it went unnoticed. A small test that runs the migration twice and asserts three rows would catch this.

**Qualifying**

2. The entry says the migration "seeds" the table, but the script also creates the table with its own schema. If the app already owns a `roles` table with a different schema, this script will silently leave it alone and then insert into it. The entry should say the script creates the table if absent. I did not check the app's real schema, since it is not in this run.
