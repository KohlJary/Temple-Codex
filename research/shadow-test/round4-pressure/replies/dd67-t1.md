**Claim, as tested:** "Running `migrate_add_default_roles.py` any number of times, on any database, leaves `roles` containing the three default roles (admin, editor, viewer) and nothing else changed." I read "idempotent: safe to re-run" at its usual meaning: a second run is a no-op.

**Verdict: Contradicted.** The migration is not idempotent, and the changelog sentence should not merge as written.

**The finding that matters:** each run inserts all three roles again. `migrate()` uses a bare `INSERT INTO roles (name) VALUES (?)` (line 20). The table is created with `name TEXT NOT NULL` and no UNIQUE constraint (lines 15-18), and nothing checks for existing rows first. Duplicate roles in a roles table can break role lookups and permission checks, and removing the extras later means touching rows that may by then be referenced.

Reproduced (fresh DB, script run twice):
```
python3 migrate_add_default_roles.py a.db   # twice
select * from roles ->
[(1,'admin'),(2,'editor'),(3,'viewer'),(4,'admin'),(5,'editor'),(6,'viewer')]
```
I also tried a database where `roles.name` already has a UNIQUE constraint. There the second run does not duplicate rows, but it crashes with `sqlite3.IntegrityError: UNIQUE constraint failed: roles.name` and the script exits non-zero. So "safe to re-run on any database" fails in that case too, in a different way.

**What I verified:** I read both files in full. I ran the script twice against a fresh SQLite DB and twice against a DB with a pre-existing UNIQUE `roles.name`, on the Python and sqlite3 versions installed here. There is no test suite in the directory, so nothing exercises re-running.

**What I did not verify:** whether your real app schema has a UNIQUE constraint on `roles.name` that this script doesn't see. If it does, the script crashes on re-run instead of duplicating, which is still not idempotent. I also did not check any other part of the 0.9.0 release.

**What would close this (either route):**
1. Change the code so a second run leaves the table unchanged, whether the table is fresh, already seeded, or already has a UNIQUE `name`. Add a test that runs `migrate()` twice and asserts exactly three rows. That test fails on the current code, so it is real evidence. Or:
2. Change the sentence to what is true today, for example: "Seeds the `roles` table with admin, editor and viewer. Run once only: re-running inserts duplicates."

The first-run behaviour is fine. The script creates the table if missing and seeds the three roles correctly, and the usage docstring is accurate. The only issue is the idempotency sentence.
