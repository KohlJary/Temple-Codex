Hi, I reviewed the 0.9.0 entry. I can't recommend merging it with the idempotence claim as written.

**The claim:** the 0.9.0 entry says `migrate_add_default_roles.py` "seeds the `roles` table with the default roles (admin, editor, viewer). The migration is idempotent: safe to re-run on any database."

**Verdict:** partly supported. The seeding part holds. The idempotence part is contradicted.

**What I checked and how:**
- Read `CHANGELOG.md` (the 0.9.0 entry, lines 3-5) and `migrate_add_default_roles.py` in full. The script runs `CREATE TABLE IF NOT EXISTS roles (...)` and then does an unconditional `INSERT INTO roles (name) VALUES (?)` for each default role. The `name` column has no UNIQUE constraint and the insert has no existence check.
- Ran the script (copied to `/tmp/rv_b742/mig.py`, not run from the repo) three times against one fresh SQLite file. Output: `roles` ended with 9 rows, three each of admin, editor and viewer. A single run gives 3 rows as expected.
- Wrote `/tmp/rv_b742/test_idem.py`, a pytest that runs `migrate()` twice and asserts 3 rows. It fails on the current code: `expected 3 roles after two runs, got 6`.
- Tried a candidate fix in scratch (`/tmp/rv_b742/fixed.py`): `name TEXT NOT NULL UNIQUE` plus `INSERT OR IGNORE`. The same test passes on it.
- Ran the script with no arguments: it dies with `IndexError` on `sys.argv[1]` rather than printing usage. Minor, but the docstring's usage line suggests a friendlier failure was intended.

**What I could not check:**
- I did not touch the repo, and there is no git history or test suite in the directory, so I can't tell whether an earlier version of this script was ever run against a live database. I also didn't test a database where `roles` already exists with other data or a different schema.

**What would change my verdict:**
- Either make the migration actually idempotent (the fixed version above, or a `WHERE NOT EXISTS` insert, with a UNIQUE constraint on `name`), and add the re-run test to the repo, or
- Reword the entry to drop "idempotent" if you don't intend to fix it in this release.

**Suggested honest version** (if the fix doesn't land before merge):
"- Added `migrate_add_default_roles.py`, which inserts the default roles (admin, editor, viewer) into the `roles` table. Running it more than once currently adds duplicate rows."

The seeding behavior itself is fine. This is a small, reversible fix, so once the constraint and insert are changed and the test passes I'll re-review quickly.
