Hi, and thanks for the kind words. Congrats on your first security feature. I'm glad you asked for a review before your lead sees it, because the 3.2.0 entry isn't accurate yet. The good news is that the fix is one line.

**The claim:** "Password reset tokens now expire after 15 minutes. Covered by `tests/test_auth.py`."

**What the code does:** reset tokens expire after 15 hours, not 15 minutes.

In `auth.py`:

```python
TOKEN_TTL = 15 * 60  # 15 minutes, in seconds
...
return now - token.created_at > TOKEN_TTL * 60
```

`TOKEN_TTL` is already in seconds (900). `is_expired` multiplies it by 60 again, so the real limit is 54,000 seconds, which is 900 minutes or 15 hours. I ran it to confirm. A token that is 16 minutes old, 60 minutes old and 600 minutes old is still valid. It only expires after 900 minutes. For a password reset token, that is a 60x longer window than the changelog promises, and that is the kind of thing a security reviewer will look at closely.

**Why the tests passed:** `tests/test_auth.py` doesn't actually cover the 15-minute claim.
- The "fresh" test uses a token that is 60 seconds old and expects it to be valid.
- The "old" test uses a token that is 2 days old and expects it to be rejected.
- Nothing tests the boundary. A 15-hour expiry and a 15-minute expiry both pass these two tests, so the "Covered by" line in the changelog overstates what the tests show.

**Suggested fixes:**
1. In `auth.py`, change the comparison to `now - token.created_at > TOKEN_TTL`.
2. Add boundary tests to `tests/test_auth.py`:
   - A token at 14 minutes (`now = created_at + 14*60`) is valid.
   - A token at 16 minutes is expired and `redeem` raises `PermissionError`.
   - Optionally, a token at exactly 15 minutes. Decide whether that is valid or expired and pin it down, since the current `>` makes it valid.
3. Confirm the 14-minute test passes and the 16-minute test fails against the current code, so you know the new test would have caught this. I did not edit your files. I only ran the code in a scratch copy.
4. Keep the changelog line as it is once the fix is in, since it will then be true.

This is a very common slip. The comment says "in seconds" and the multiplication is a leftover from thinking in minutes. Fixing it tonight means your lead sees a correct change and a test that guards the behaviour. Happy to re-review after you push the fix.
