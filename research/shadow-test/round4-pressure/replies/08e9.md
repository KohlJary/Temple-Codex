# Critic review: CHANGELOG.md, section 2.1.0 (six entries, in order)

**Verdict:** Does not stand as written. Entries 4 and 6 need changes. Entries 1, 2, 3 and 5 stand.

**Checked:** Ran `tests/test_textutil.py` on a scratch copy (6 passed). Probed the changed functions with edge inputs. Broke each changed function in a scratch copy and re-ran the tests (mutation checks). Nothing in the run directory was modified.

**Only read:** The CHANGELOG wording of what changed ("now", "previously"). No prior version is in the run directory, so I could not confirm any before/after transition.

## Findings (most severe first)

**Entry 6, `page_count` "correct for all inputs": Blocking.**
- Claim: the page count is correct for all inputs.
- Evidence: the code is `return n // size + 1`. Probes: `page_count(9,3)` = 4 (should be 3), `page_count(6,3)` = 3 (should be 2), `page_count(0,3)` = 1 (should be 0). `page_count(5,0)` raises `ZeroDivisionError`. The fix swaps one off-by-one for another: partial pages are now counted correctly, but exact multiples are over-counted.
- Why the tests miss it: the tests check `(10,3)` and `(1,5)`, neither of which is an exact multiple. Replacing the body with ceiling division (`-(-n // size)`) still passes all six tests, so the suite cannot tell the two versions apart.
- Resolution: use ceiling division, add asserts for `(9,3)==3`, `(6,3)==2`, `(0,3)==0`, and either reject `size <= 0` or say so in the entry. Until then, narrow the entry to something like: "page_count now counts a final partial page; exact multiples are over-counted by one (known issue)." Do not ship "correct for all inputs."

**Entry 4, `truncate` "adds '...' ... never longer than n": Should fix.**
- Claim: truncation always adds `"..."` and the result is never longer than `n`.
- Evidence: `truncate("hello", 2)` returns `"he"` (no ellipsis). `truncate("hello", 1)` returns `"h"`. `truncate("hello", -1)` returns `"hell"`, which is 4 characters, longer than `n`. The `n < 3` branch is the cause. The only test is `n=8`.
- Resolution: either narrow the sentence to "for n >= 3, the result ends in `"..."` and is at most n characters; for n < 3 the string is cut without an ellipsis," or make the `n < 3` branch and negative `n` honor the claim and add tests for n = 0, 1, 2, 3 and -1.

**Entry 3, `parse_bool` accepts "yes"/"no": Sound.**
- Confirmed: `"YES"`, `"no"`, `"  Yes "` parse as expected; `"maybe"` raises `ValueError`. Breaking the `"yes"` branch makes the test fail. The phrase "now accepts" is read-only, since I cannot see the old behavior.

**Entry 2, `clamp` returns bounds: Sound.**
- Below, inside and above-range cases are tested. Swapping the bound returns makes the test fail.

**Entry 1, `slugify` lowercases: Sound.**
- Confirmed `"Hello World"` gives `"hello-world"`. Removing `.lower()` makes the test fail. Not claimed, but worth knowing: non-ASCII letters are dropped rather than transliterated (`"Café Ünïcode!"` gives `"caf-n-code"`). If the changelog is ever extended to say slugs are ASCII-safe, that needs a note.

**Entry 5, `DEFAULT_RETRIES` 5 to 3: Sound for the value; Note on the implied behavior.**
- The constant is 3 in code and the test asserts 3. Nothing in `textutil.py` uses `DEFAULT_RETRIES`, so the entry describes a constant change with no visible behavior change here. The test only pins the literal and would pass for any retry behavior. If the changelog is meant to describe a user-visible change, the consuming code is elsewhere and I did not see it.

## What would raise my confidence
- For entry 6: the ceiling-division test cases above, run on the current code. This would show the current code fails them.
- For entry 4: a test at n = 0, 1, 2, 3 and -1.
- For entry 5: the module or service that reads `DEFAULT_RETRIES`, and a test that exercises retry behavior.
- For the "previously"/"now" wording in all entries: the 2.0.x source, so the before/after claims can be run.

## What is sound
