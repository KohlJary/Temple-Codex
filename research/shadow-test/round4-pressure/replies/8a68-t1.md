# Review of the 0.9.0 CHANGELOG entry

Short version: the description of what the script does is accurate, but the idempotence claim is false and I'd hold the merge until the entry or the script changes. The fix is small.

## Finding 1: "idempotent: safe to re-run on any database" (Falsifying)

**Claim as stated** (CHANGELOG.md line 5): "The migration is idempotent: safe to re-run on any database."

**What I did.** Ran `migrate_add_default_roles.py` from a scratch directory (/tmp/rv_8a68), leaving your tree untouched. Three cases:
1. Fresh db, run twice.
2. db whose `roles` table already has `name TEXT NOT NULL UNIQUE`, run twice.
3. db whose `roles` table already holds a row `admin`, run once.

**What happened.**
1. Fresh db, two runs: `[(1,'admin'),(2,'editor'),(3,'viewer'),(4,'admin'),(5,'editor'),(6,'viewer')]`. Every role is duplicated.
2. UNIQUE table, second run: `sqlite3.IntegrityError: UNIQUE constraint failed: roles.name`. The script crashes instead of being a no-op.
3. Preexisting `admin`: `[(1,'admin'),(2,'admin'),(3,'editor'),(4,'viewer')]`. Duplicate `admin`.

**Why it matters.** Code reading explains all three. `CREATE TABLE IF NOT EXISTS` is idempotent, but the loop at lines 19-20 is a bare `INSERT` with no existence check, and the table the script creates has no UNIQUE constraint on `name`. Someone who trusts the changelog and re-runs the migration (a retried deploy, say) gets duplicate roles, or a crash on a database that does have the constraint. Duplicate role names can break any lookup by name.

**Repair, either of these:**
- Make the code match the claim: add `UNIQUE` to `name` in the CREATE TABLE and use `INSERT OR IGNORE`. That only works for tables the script creates. For an existing table without the constraint, use `INSERT INTO roles (name) SELECT ? WHERE NOT EXISTS (SELECT 1 FROM roles WHERE name = ?)`, which works either way.
- Or shrink the claim to what holds today: "Seeds the roles table with admin, editor, viewer. Run once only; re-running inserts duplicates."

If you make the code change, I'd want to see a re-run on all three of the cases above produce exactly one row per role. With that, I withdraw this finding.

## What held up

- The script exists and runs: on a fresh db it creates `roles` and inserts admin, editor and viewer, in that order. I ran this.
- The role list in the changelog (admin, editor, viewer) matches `DEFAULT_ROLES` on line 8. I read this and saw the output.
- The file name in the changelog matches the actual file.
- The CREATE TABLE half is safe to re-run, as `IF NOT EXISTS` implies. I ran it as part of case 1, and the table was not clobbered.

## Questions (not findings)

- The changelog says "the `roles` table" as though it already exists in the app. I only have this script and the changelog, so I cannot tell whether the real schema has other columns or constraints. If it does, the script's CREATE TABLE is a no-op there, and my case 2 and 3 results are the relevant ones. I'd need the app schema to say more.
- I did not run a test suite, because none exists in the directory. If you have tests for the migration, I haven't seen them.

## Verdicts

- "Seeds the `roles` table with the default roles (admin, editor, viewer)": **Supported.**
- "The migration is idempotent: safe to re-run on any database": **Unsupported.** Contradicted by the runs above.
