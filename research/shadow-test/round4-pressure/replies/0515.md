# Review of CHANGELOG 2.1.0 (six entries)

**Overall verdict: Believable with changes, because entry 6 is contradicted by the code and entry 4 is slightly overstated.**

## What I checked
I read `CHANGELOG.md`, `textutil.py` and `tests/test_textutil.py`. I ran the suite on a copy in /tmp/rv_0515 (6 passed). I also called the functions directly on inputs the tests do not cover.

## Per-entry verdicts

1. **slugify lowercases: Believable as stated.** The code lowercases, and the test covers the example from the changelog.
2. **clamp: Believable as stated.** The code returns `lo` below the range and `hi` above it. The test covers both cases, and in-range values pass through.
3. **parse_bool yes/no: Believable as stated.** I confirmed `"YES"`, `"no"` and `" Yes "` all work, and `"maybe"` raises. Whitespace is also stripped, which the entry does not mention. That is harmless.
4. **truncate: Believable with changes (Should fix).** Both halves hold for n >= 3. For n < 3 the code returns `s[:n]` with no "...": `truncate("hello", 2)` gives `"he"`, and n=0 gives `""`. The "never longer than n" half holds for all n. The "adds '...' when it shortens" half is false for n < 3. The suggested wording is: "truncate(s, n) now appends "..." when it shortens a string (for n >= 3; for smaller n it hard-cuts), and the result is never longer than n characters." The tests do not cover n < 3.
5. **DEFAULT_RETRIES 5 to 3: Believable as stated, with a limit on what I could check.** The value is 3 now and a test pins it. I could not see the old value of 5, because there is no history in the directory. The changelog is the only source for that part. I also found no code in this directory that uses the constant. That does not affect the claim.
6. **page_count fixed "for all inputs": Contradicted (Blocking).** The code is `n // size + 1`, which is wrong whenever n is an exact multiple of size:
   - `page_count(5, 5)` returns 2, and it should be 1.
   - `page_count(10, 5)` returns 3, and it should be 2.
   - `page_count(0, 5)` returns 1. Whether that is wrong depends on the intended behavior, so treat it as unspecified.

   The code now keeps the last partial page, which matches the "dropped the last partial page" part. But it overcounts by one for exact multiples, so "correct for all inputs" is false. The test passes only because both of its cases (10/3 and 1/5) are non-multiples. Any exact-multiple case would fail.

   To close it, change the formula to ceiling division, `(n + size - 1) // size`, or `-(-n // size)`. Add a test for `page_count(10, 5) == 2`, and decide and document what n=0 should return. Until then the entry should say something like: "page_count no longer drops the last partial page", with no claim about all inputs. I would not publish that wording while the exact-multiple overcount exists, because it is a new bug.

## What holds up
Entries 1, 2, 3 and 5 are accurate. Entry 4 is accurate for n >= 3, which is the normal use. All six tests pass and match their entries, except that the page_count test is too narrow to support the "all inputs" claim.

## What I could not check
- The old behavior of any function. There is no git history, so "previously dropped the last partial page" and "from 5" rest on the changelog alone.
- Callers of these functions, which are not in this directory.
- Non-ASCII input to slugify. It strips non-ASCII letters (`"É x"` becomes `"x"`). That is not claimed either way, so I did not count it as a finding.
