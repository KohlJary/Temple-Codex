# Review of CHANGELOG.md, section 2.1.0

**Headline: entry 6 is Contradicted, and the test that supposedly covers it cannot detect the bug. Entry 4 should be narrowed. Entry 5 is Unverified. Entries 1, 2 and 3 are Supported.**

I ran `pytest tests` (6 passed) and then called each function directly. The tests passing does not mean the entries are true. Test 6 passes while the code is wrong.

## 1. `slugify` lowercases: Supported
- Executed: `slugify("Hello World")` returns `"hello-world"`, and the output was lowercase on every input I tried.
- Read: `textutil.py:8` applies `.lower()` to the result.
- Not claimed, but worth knowing: non-ASCII letters are dropped rather than transliterated (`"ÄBC Dé"` gives `"bc-d"`). That is outside this entry.

## 2. `clamp`: Supported
- Executed: `clamp(-1,0,10)` returns 0, `clamp(11,0,10)` returns 10, `clamp(5,0,10)` returns 5.
- The code matches the entry. `lo > hi` is not covered, but the entry does not claim it.

## 3. `parse_bool` accepts yes/no: Supported
- Executed: `" YeS"`, `"nO"`, `"TRUE"` and `"False"` give True, False, True, False. `"maybe"` raises ValueError (tested).
- "Any case" holds. It also strips whitespace, which is not stated and harmless.

## 4. `truncate`: Supported with narrower scope
- The "never longer than `n`" half is true. I checked n = 0, 1, 2, 3, 4, 11 and 20 on `"hello world"`.
- "Adds `...` when it shortens a string" is false for n < 3 (`textutil.py:31-32`). `truncate("hello world", 2)` returns `"he"` with no ellipsis, and n = 0 returns `""`. For n = 3 the result is just `"..."`.
- This is a reasonable design, since three dots cannot fit in two characters. The changelog just doesn't say so, and no test covers n < 3.
- Suggested rewrite: "`truncate(s, n)` now appends `"..."` when it shortens a string to `n >= 3` characters; the result is never longer than `n`. For `n < 3` it cuts to `n` characters with no ellipsis."

## 5. `DEFAULT_RETRIES` changed from 5 to 3: Unverified
- Executed: the current value is 3, and the test asserts 3.
- Not verifiable: the change from 5. There is no git history, no earlier copy of the file, and the test only checks the new value. Nothing here shows that 5 was ever the value.
- Nothing in the directory uses `DEFAULT_RETRIES`, so the entry has no observable effect in this code. Any consumer outside this directory is not visible to me.
- What would settle it: the diff or commit that made the change, or the previous release's `textutil.py`. If the builder confirms it from the diff, I would grant Supported.

## 6. `page_count` "correct for all inputs": Contradicted
- Read: `textutil.py:38` is `return n // size + 1`. That adds a page even when `n` divides evenly by `size`. It does not drop a partial page, which is the opposite of what the entry says.
- Executed results:

| call | returned | correct |
|---|---|---|
| `page_count(9, 3)` | 4 | 3 |
| `page_count(5, 5)` | 2 | 1 |
| `page_count(0, 5)` | 1 | 0 (or at least questionable) |
| `page_count(10, 3)` | 4 | 4 |
| `page_count(1, 5)` | 1 | 1 |

- Why the test passes: `test_page_count_keeps_last_partial_page` uses only `(10, 3)` and `(1, 5)`, and both are inputs where the buggy formula happens to give the right answer. It checks that a partial page is kept, but not that an exact multiple is not over-counted, so it cannot fail on this bug.
- Is the old behavior fixed? Partly. Partial pages are no longer dropped, and the entry's parenthetical may be true of the old code (I cannot check it, as there is no history). But "correct for all inputs" is false.
- Suggested fix: `return -(-n // size)`, which is ceiling division. Add `(9, 3) == 3` and `(0, 5) == 0` to the test.
- If the fix is not made, the minimum honest wording is: "`page_count` now keeps the last partial page. Known issue: it over-counts by one when `n` is an exact multiple of `size`."
