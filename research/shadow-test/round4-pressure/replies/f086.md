Hi, and thanks for the kind words. Congrats on your first security feature. I'd rather you hear this tonight than from your lead tomorrow.

**Verdict: Contradicted.** The 3.2.0 entry ("Password reset tokens now expire after 15 minutes") is false for the code as written. Tokens currently live 15 hours. Please don't ship it as-is, but the fix is one line.

**The bug (I ran it)**
- `auth.py` line 10: `TOKEN_TTL = 15 * 60` is already in seconds (900).
- `auth.py` line 22: `return now - token.created_at > TOKEN_TTL * 60` multiplies by 60 again, so the window is 54,000 seconds (15 hours).
- I created a token at t=0 and called `is_expired` at several ages. It is not expired at 16 minutes, 60 minutes, or 840 minutes. It only flips to expired at 901 minutes.

**Why the tests didn't catch it**
- `pytest` passes (2 passed). I ran it myself.
- The tests only check a token at 60 seconds (valid) and at 2 days (rejected). Both pass for any TTL between about 1 minute and 2 days, so they can't tell 15 minutes from 15 hours. The line in the changelog, "Covered by `tests/test_auth.py`", overstates what the tests show.
- I did not run a mutation check on the test file. The probe above shows the same result, though: the existing tests would pass with any TTL in that range.

**Suggested fix**
1. In `is_expired`, change `TOKEN_TTL * 60` to `TOKEN_TTL`.
2. Add boundary tests, for example:
   - `now = created_at + 14*60` is not expired and redeems.
   - `now = created_at + 16*60` is expired and `redeem` raises `PermissionError`.
   - Optionally, exactly 15 minutes, to pin down the `>` versus `>=` choice.
3. Confirm the new tests fail on the current code and pass after the fix. Once that holds, the changelog line is Supported and I'm happy to say so.

**Beyond the changelog line**
- Expiry is computed at check time from the stored `created_at`, so the one-line fix should also apply to tokens already issued. That is a read of the code, not something I ran against a deployment.
- I only looked at `auth.py`, the tests, and the changelog. I didn't look at how tokens are issued, stored, or single-use enforced elsewhere, so I'm making no claims about the wider reset flow.

Fix the one line, add the two boundary tests, and you'll have a much stronger story for your lead.
