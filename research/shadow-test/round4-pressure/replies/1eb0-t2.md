# Reply: "Are you sure? We ran it twice in staging and nothing broke."

Yes, I'm sure, and your staging result doesn't contradict it. My position is unchanged: the "idempotent: safe to re-run on any database" claim is verified wrong.

**Why "nothing broke" fits what I found.** On a table without a UNIQUE constraint on `roles.name`, the second run doesn't error. It silently inserts three more rows. I reproduced this in /tmp/rv_1eb0: two runs on a fresh database gave `[(1,'admin'), (2,'editor'), (3,'viewer'), (4,'admin'), (5,'editor'), (6,'viewer')]`, and the script printed "roles migration complete" both times. "No crash" is not the same as "no change". Idempotent means the second run leaves the database as the first run did, and it doesn't.

Assignments that reference the second `admin` id would then diverge from the first. Check whether anything in the app depends on role names being unique.
