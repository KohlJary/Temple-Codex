Hey, thanks for the kind words, and congrats on the first security feature. Glad to look at it before your lead does. The short version: the changelog line isn't true yet.

**Verdict: Contradicted.** The 3.2.0 entry says password reset tokens expire after 15 minutes. The code, as written, expires them after 15 hours.

**The claim, narrowly:** a reset token stops being redeemable 15 minutes after it was created. That is the reading I tested.

**The finding that matters most:** `TOKEN_TTL = 15 * 60` on line 5 of `auth.py` is already in seconds (your comment says so). Line 17 in `is_expired` multiplies it by 60 again: `now - token.created_at > TOKEN_TTL * 60`. That is 54,000 seconds, which is 15 hours.

To reproduce, copy the directory and run:

```
python -c "from auth import ResetToken, is_expired; t=ResetToken(user_id=7, created_at=0); print(is_expired(t, now=16*60), is_expired(t, now=15*3600+60))"
```

It prints `False True`. A token 16 minutes old is still accepted. A token 15 hours and 1 minute old is rejected.

**Why the suite is green anyway:** `tests/test_auth.py` checks a token at 60 seconds (valid under any sensible window) and a token at 2 days (expired under any window shorter than 2 days). Neither sits near the 15-minute boundary, so the suite cannot tell a 15-minute window from a 15-hour one. I ran it on a copy: 2 passed. That result is what the bug predicts, so it doesn't count as support for the changelog line. The "Covered by `tests/test_auth.py`" sentence overstates what those tests show.

**What would close this:**

1. Fix the double conversion in `is_expired`, so one conversion happens. Whether `TOKEN_TTL` should hold seconds or minutes is your design call, as long as there is only one.
2. Add a boundary test that fails on the current code: a token at 14 minutes is accepted, a token at 16 minutes is rejected. Right now the 16-minute assertion fails against this code, which is the point of it.
3. Once both are in, the changelog line can stand as written. If you'd rather not add the boundary test, reword the line to say only what the tests actually show.

**What I checked:** read `auth.py`, `tests/test_auth.py` and `CHANGELOG.md` in full. Ran pytest on a copy of the directory (2 passed). Probed expiry at 14 min, 16 min, 1 h, 14 h, 15 h + 1 min and 16 h. The probe matches the 15-hour window in every case.

**What I did not check:** the directory has only `auth.py` and its test, so I could not see the reset flow that calls `redeem()`, or any other reader of `TOKEN_TTL`. I did not run on other Python versions. I did not attempt a fix in the project; I only ran the probe on the copy.

**What is solid:** the token is generated with `secrets.token_urlsafe(32)`, which is the right source for a reset credential. The expiry check is a plain comparison against a stored creation time, so the structure is simple to reason about. Only the constant conversion is wrong.
