# Review of CHANGELOG.md 0.9.0

**Recommendation: do not merge as written.** The "idempotent: safe to re-run on any database" claim is verified wrong. The rest of the entry is accurate.

## Finding 1 (Verified wrong): the migration is not idempotent

`migrate_add_default_roles.py` lines 17-18 run a plain `INSERT INTO roles (name) VALUES (?)` for each default role. Nothing checks whether the row already exists, and the `CREATE TABLE IF NOT EXISTS` at line 11 has no UNIQUE constraint on `name`. I ran it in a scratch directory (/tmp/rv_1eb0), not in your run directory.

- **Fresh database, run twice.** The roles table ends up as `[(1,'admin'), (2,'editor'), (3,'viewer'), (4,'admin'), (5,'editor'), (6,'viewer')]`. Every re-run adds three more duplicate rows.
- **Database whose `roles.name` is UNIQUE, with `admin` already present.** The script crashes with `sqlite3.IntegrityError: UNIQUE constraint failed: roles.name`. The insert and commit are not wrapped in error handling, so the migration aborts partway.

So re-running is not safe on a database the script created itself, and it is not safe on a differently-defined `roles` table either. "Any database" is the strongest wording in the entry, and it is contradicted twice.

**Fix, your call:**
- Use `INSERT OR IGNORE`, or `INSERT ... WHERE NOT EXISTS (SELECT 1 FROM roles WHERE name = ?)`.
- Add `UNIQUE` to `name` in the `CREATE TABLE`, so the guarantee lives in the schema.
- Note that `INSERT OR IGNORE` alone only helps if a UNIQUE constraint exists. Without one it still duplicates, so use the `WHERE NOT EXISTS` form or add the constraint.
- Add a test that runs `migrate()` twice and asserts three rows.

**Wording if you ship it unchanged:** "Added `migrate_add_default_roles.py`, which seeds the `roles` table with admin, editor and viewer. Run it once per database; re-running creates duplicate rows." That is true today, but fixing the code is better.

## Finding 2 (Overstated, minor): "seeds the roles table"

If a `roles` table already exists with extra required columns, the insert fails. I did not test this case; it is a guess from reading the code. It matters little once Finding 1 is addressed.
