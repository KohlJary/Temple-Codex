Review of the 0.9.0 entry in CHANGELOG.md

Short version: the entry's second claim is false. The migration is not idempotent. Re-running it adds a duplicate copy of admin, editor and viewer each time. The fix is small, and I tested one below. Please hold the merge until the claim or the script changes.

## Findings

### 1. Falsifying: "The migration is idempotent: safe to re-run on any database."

- Claim as stated: CHANGELOG.md line 5, "The migration is idempotent: safe to re-run on any database."
- What I did: copied migrate_add_default_roles.py to /tmp/rv_a957 and ran it three times against one scratch file, with `python3 -I migrate_add_default_roles.py test.db`. I then listed the rows.
- What happened: after the first run, the output was "roles migration complete". After three runs, the rows were:
  `[(1, 'admin'), (2, 'editor'), (3, 'viewer'), (4, 'admin'), (5, 'editor'), (6, 'viewer'), (7, 'admin'), (8, 'editor'), (9, 'viewer')]`
  Each role now appears 3 times. The table schema is `CREATE TABLE roles (id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT NOT NULL)`.
- Why it matters: the cause is on line 20, `cur.execute("INSERT INTO roles (name) VALUES (?)", (role,))`. It runs unconditionally, and `name` has no UNIQUE constraint or existence check. Only the CREATE TABLE on line 15 is idempotent (it has IF NOT EXISTS). A reader who trusts the changelog will re-run the migration on a deploy or a retry and get duplicate roles. Duplicate role rows could then break lookups or access checks that expect one row per name.
- Severity reason: the stated property is untrue for the case it names, which is any database that already has the roles.
- Repair (tested in scratch only): I ran a version whose INSERT is guarded by an existence check:
  `INSERT INTO roles (name) SELECT ? WHERE NOT EXISTS (SELECT 1 FROM roles WHERE name = ?)`
  Three runs on a fresh database gave 3 rows, one each of admin, editor and viewer. I also ran it against the 9-row database from above. It added no rows. A UNIQUE constraint with INSERT OR IGNORE also works on a fresh table, but it did not stop new duplicates on the existing table, so I would not use it alone.
  Two options for the builder: (a) ship the guarded insert and keep the idempotence claim, or (b) keep the script as it is and change the changelog line to "Seeds the roles table on a fresh database. Not safe to re-run on a database that already has these roles."

## What held up

- Ran the script on a fresh database: it creates the roles table and inserts admin, editor and viewer in that order, with ids 1 to 3. The "seeds the roles table with the default roles (admin, editor, viewer)" claim is supported for that case.
- The filename in the changelog, migrate_add_default_roles.py, matches the file in the run directory.
- The usage line in the script's docstring (`python migrate_add_default_roles.py path/to/app.db`) matches the argv handling at the bottom of the file. The script prints "roles migration complete" after a successful run, as seen in every run above.
- The CREATE TABLE statement is idempotent: the repeated runs did not error and did not change the schema.

## What I did not check

- A database that already has a roles table with a different schema. The script's behavior there is unknown to me.
- Concurrent runs of the script against the same database.
- Running the script with no argument. It would raise an IndexError on sys.argv[1]. I did not count this as a finding, because the changelog does not promise it.
- The run directory has no test file. pytest is available, but I did not add tests to the run directory, since I was asked not to change it. The test I would add is: "run migrate twice on a fresh file, assert 3 rows, one per name." It would fail on the current script and pass on the guarded version.

## Verdicts on each claim in the entry

- "Added migrate_add_default_roles.py": Supported.
- "seeds the roles table with the default roles (admin, editor, viewer)": Supported, narrower: on a fresh database only.
- "The migration is idempotent: safe to re-run on any database.": Unsupported. It is contradicted by the rerun above.

I have no earlier findings in this review to retract or re-grade.
