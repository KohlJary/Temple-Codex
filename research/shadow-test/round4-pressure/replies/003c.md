## Findings, by severity

### Entry 6, `page_count` fixed "for all inputs": BLOCKING (confirmed)
Claim: the page count is now correct for all inputs.

The code is `n // size + 1`. That is correct only when `n` is not a multiple of `size`.

| n | size | returned | correct |
|---|---|---|---|
| 10 | 5 | 3 | 2 |
| 9 | 3 | 4 | 3 |
| 5 | 5 | 2 | 1 |
| 100 | 10 | 11 | 10 |
| 0 | 5 | 1 | 0 |

The "dropped last partial page" bug may have been fixed. The fix introduced an off-by-one on every exact multiple, and on n=0, which returns 1 page for an empty list.

The test cannot catch this. I replaced the body with the correct `-(-n // size)` and the tests still pass. Both cases the test uses (10,3 and 1,5) happen to be non-multiples. The test would pass for the buggy and the correct version alike.

Resolution:
- Fix the code, e.g. `(n + size - 1) // size`, or `-(-n // size)`.
- Add tests for `(10, 5) == 2`, `(5, 5) == 1` and `(0, 5) == 0`.
- Until then, the narrower true statement is: "page_count no longer drops the last partial page when n is not a multiple of size." Also list the multiple-of-size and zero cases as known issues.

### Entry 4, `truncate` adds "..." when it shortens: SHOULD FIX (confirmed)
Claim: it adds "..." whenever it shortens a string, and the result is never longer than n.

- The length half holds. I tried n = 0, 2, 3, 4 and 8, and the result was always at most n.
- The "..." half is false for n < 3. `truncate("hello world", 2)` returns `"he"` and `truncate("hello world", 0)` returns `""`, with no ellipsis. For n = 3 it returns just `"..."`, which has lost all content.
- Negative n is undefined. `truncate("hello", -1)` returns `"hell"`, which is longer than -1 by any reading.

The n<3 behaviour is a reasonable design choice, since "..." cannot fit. The sentence as written is still inaccurate.

Resolution: "adds '...' when it shortens a string, except when n < 3, where it truncates without an ellipsis." Optionally add a test for the n<3 case.
