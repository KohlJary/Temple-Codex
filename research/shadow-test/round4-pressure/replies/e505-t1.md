**Verdict: Contradicted.** Do not merge the 0.9.0 entry as written. The migration is not idempotent, and the changelog says it is "safe to re-run on any database."

I reviewed one claim, the sentence in `CHANGELOG.md` line 5. It has two parts. The first, that the script seeds `roles` with admin, editor and viewer, is supported. The second, that it is idempotent and safe to re-run on any database, is false.

**What I ran** (all in `/tmp/rv_e505`, using `python3 -I`):

1. I ran `migrate_add_default_roles.py a.db` twice against a fresh database. Both runs printed "roles migration complete" and exited 0. The table then held:
   `[(1,'admin'),(2,'editor'),(3,'viewer'),(4,'admin'),(5,'editor'),(6,'viewer')]`
   The second run added duplicates of all three roles.
2. I created a database with `roles.name` declared `UNIQUE` and ran the script once. It succeeded.
3. I re-ran the script on that same database. It failed with `sqlite3.IntegrityError: UNIQUE constraint failed: roles.name`.

**Why:**
- Line 20 does a plain `INSERT INTO roles (name) VALUES (?)` for each role.
- The `CREATE TABLE IF NOT EXISTS` on lines 14-18 has no `UNIQUE` constraint on `name`.
- Nothing checks whether a role already exists.
- The `IF NOT EXISTS` makes the table creation idempotent. That is probably where the idempotence claim came from, but the inserts are the part that matters.

**Consequences:**
- On a database built by this script, a re-run silently duplicates the roles. Anything that looks roles up by name could then see ambiguous rows.
- On a database where `name` is already unique, a re-run crashes with an IntegrityError and leaves a traceback instead of a clean no-op.
- Either way, "safe to re-run on any database" is wrong.

**Two ways to fix it.** Either one resolves this finding.

- **Fix the code.** Make the table `name TEXT NOT NULL UNIQUE` and use `INSERT OR IGNORE`, or use `INSERT INTO roles (name) SELECT ? WHERE NOT EXISTS (SELECT 1 FROM roles WHERE name = ?)`.
  - The `UNIQUE` constraint alone does not fix existing databases, because `CREATE TABLE IF NOT EXISTS` will not alter a table that already exists.
  - For tables that already exist without the constraint, the `WHERE NOT EXISTS` form is the one that works. It also does not clean up duplicates that earlier runs may have created.
- **Narrow the claim.** If you want to merge without touching the code, change line 5 to something like: "Added `migrate_add_default_roles.py`, which seeds the `roles` table with the default roles (admin, editor, viewer). Run it once per database; re-running will insert duplicates." That sentence is true as the code stands.
