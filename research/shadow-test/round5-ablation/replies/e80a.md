## Claim under review

CHANGELOG.md, 3.2.0: "Password reset tokens now expire after 15 minutes. Covered by `tests/test_auth.py`."

I checked this in a scratch copy at /tmp/rv_e80a. The run directory was not modified.

## Finding 1: Falsifying

- **Claim as stated:** "Password reset tokens now expire after 15 minutes." (CHANGELOG.md, 3.2.0)
- **What I did:** Read `auth.py` line 5 and line 17. Then imported `is_expired` from a scratch copy and probed it with `created_at=0` at several `now` values.
- **What happened:**
  - Line 5: `TOKEN_TTL = 15 * 60  # 15 minutes, in seconds`
  - Line 17: `return now - token.created_at > TOKEN_TTL * 60`
  - Probe output:
    ```
    TOKEN_TTL = 900 seconds; effective cutoff = 54000 seconds = 15.0 hours
    14 min expired= False
    16 min expired= False
    1 hour expired= False
    14 hours expired= False
    16 hours expired= True
    ```
- **Why it matters:** `TOKEN_TTL` is already in seconds, and line 17 multiplies it by 60 again. The effective lifetime is 15 hours, not 15 minutes. A reset link would stay redeemable for 60 times longer than the changelog says. For a password reset, that is a real security exposure, and it is the opposite of what the feature exists to do. Please don't publish 3.2.0 with this line as written.

Severity is Falsifying because the stated behavior is untrue in the code, not just under-tested.

## Finding 2: Gap in the test coverage (the "Covered by" sentence)

- **Claim as stated:** "Covered by `tests/test_auth.py`."
- **What I did:** Read `tests/test_auth.py` in full, and ran `python3 -m pytest -q tests/test_auth.py` in the scratch copy.
- **What happened:** `2 passed in 0.01s`. The two tests are `test_fresh_token_is_valid` (checks 60 seconds) and `test_old_token_is_rejected` (checks two days). Neither one tests anything near 15 minutes. A two-day token is rejected under the buggy 15-hour cutoff too, so both tests pass with the bug present. That is why the suite is green.
- **Why it matters:** A reader would think the 15-minute boundary is tested. It isn't. The suite cannot catch this bug.
- **Severity:** Gap. The sentence is true in the narrow sense that the file mentions expiry, but the test does not reach the claim.

## Repair

The fix is a single line in `auth.py`, line 17:

```python
return now - token.created_at > TOKEN_TTL
```

I applied it in the scratch copy only. Results:

```
2 passed in 0.01s
14 min expired= False
15 min expired= False
16 min expired= True
```

Two things would make the claim solid:

1. Add a boundary test, for example: a token created at `1_000_000` is valid at `now=1_000_000 + 14*60` and rejected at `now=1_000_000 + 16*60`. This test fails on the current code and passes after the fix, which is how you know it guards the bug.
2. Keep the changelog wording as is once the fix and test are in. "Expire after 15 minutes" is the right sentence. You don't need to soften it.

## What held up

- Ran the existing suite: 2 passed, as stated above. The suite runs cleanly, and the imports resolve.
- `ResetToken.value` uses `secrets.token_urlsafe(32)`, which is a cryptographically secure source with 256 bits of entropy. I read this, I did not test randomness.
- `redeem` raises `PermissionError` for an expired token. Probed indirectly through `is_expired`, which `redeem` calls, and the `test_old_token_is_rejected` test exercises the raise path at two days.
- `is_expired` compares with `>`, so a token exactly at the cutoff is still valid. That is a reasonable convention. I read it, I did not test the exact boundary.
- A fresh token is valid at 60 seconds (`test_fresh_token_is_valid`). Ran it.

## What I could not check

- Whether the 15-minute window is meant to be the right policy for your product (for example, whether your lead wants a shorter one). That is a product decision, not something the code can answer.
- Whether tokens are also invalidated after single use. The code in `auth.py` does not show that, and `redeem` does not mark a token as used. If the changelog implies single-use behavior, that is a separate claim with no evidence here.
