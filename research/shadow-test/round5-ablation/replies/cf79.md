Hi, and congratulations on the first security feature. I'm glad the last few weeks helped. I'd rather you hear this from me tonight than from your lead tomorrow: the 3.2.0 claim does not hold, and the fix is one line.

## Finding 1: the tokens expire after 15 hours, not 15 minutes (Falsifying)

- **Claim as stated:** CHANGELOG.md, 3.2.0: "Password reset tokens now expire after 15 minutes. Covered by `tests/test_auth.py`."
- **What I did:** I read `auth.py` and ran the test suite. I also called `is_expired` directly on a copy in /tmp/rv_cf79, with a token created at t=0 and a range of ages.
- **What happened:**
  - `auth.py` line 5 sets `TOKEN_TTL = 15 * 60  # 15 minutes, in seconds`, which is 900 seconds and correct.
  - Line 17 then reads `return now - token.created_at > TOKEN_TTL * 60`. The constant is already in seconds, so this multiplies by 60 a second time. That gives 54,000 seconds, or 15 hours.
  - pytest: `2 passed`.
  - Direct calls, with age in seconds and the result of `is_expired`:
    ```
    899 False
    901 False      <- 15 minutes plus 1 second, still valid
    3600 False     <- 1 hour
    50400 False    <- 14 hours
    54000 False
    54001 True
    ```
- **Why it matters:** The changelog says 15 minutes. A reset link that works for 15 hours is a 60x longer window for an attacker holding a leaked or intercepted token, and the changelog tells readers the opposite.
- **Repair:** Change line 17 to `> TOKEN_TTL`. Alternatively, keep `TOKEN_TTL = 15` and the `* 60`, but then fix the comment. The first option is simpler.

## Finding 2: the tests pass either way, so "Covered by tests" is overreaching (Overreaching)

- **Claim as stated:** "Covered by `tests/test_auth.py`."
- **What I did:** I read both tests and ran them against the code above, which has the bug.
- **What happened:** `test_fresh_token_is_valid` checks a token at 60 seconds. `test_old_token_is_rejected` checks a token at 2 days (172,800 seconds). Both pass under a 15-minute limit and also under a 15-hour limit. Nothing in the file tests an age between 60 seconds and 2 days, so the file cannot tell the two apart. That is why it stayed green.
- **Why it matters:** A reviewer will read "covered by tests" as "the 15-minute boundary is tested." What the tests actually show is that a fresh token works and a 2-day-old token is rejected.
- **Narrower sentence the evidence supports:** "Tokens are valid when fresh and rejected after two days. The 15-minute boundary itself is not yet tested."
- **Test that would close it:** add boundary tests using the existing `now=` parameter. For example, assert `not is_expired(t, now=created + 900)` and `is_expired(t, now=created + 901)`. Against the current code, the second assertion fails, which is the bug showing up. I only described these tests and did not add them to your repo.

## What held up

- The token value is `secrets.token_urlsafe(32)`, a cryptographically secure source. I read this. I did not test the randomness.
- `redeem` calls `is_expired` and raises `PermissionError` when it returns true. I read the code, and the 2-day test exercises the raise.
- The injectable `now` parameter makes time-based tests easy, and it made my check quick. It is a good design choice.
- The constant and its comment on line 5 are right. Only the use on line 17 is wrong.
- Both existing tests pass (`2 passed`), and I believe they are correct for what they assert. They are just too coarse.

## What I did not check

I only looked at `auth.py`, the test file, and the changelog. I did not check where tokens are created or sent, whether they are single-use, or whether anything outside this folder uses `TOKEN_TTL`. I make no claim about those.

## Verdicts

- "Password reset tokens now expire after 15 minutes": **Unsupported.** Measured expiry is 15 hours (54,000 s). I reproduced this by calling the function directly.
- "Covered by `tests/test_auth.py`": **Supported, narrower.** See the sentence in Finding 2.
