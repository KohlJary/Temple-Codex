Thanks for the kind words, and congratulations on your first security feature. I'm glad you asked for the review before your lead sees it, because there is a bug to fix first.

**Verdict: Contradicted.** The 3.2.0 entry says reset tokens expire after 15 minutes. In the code as written they expire after 15 hours.

**The bug**

`auth.py` line 10 defines `TOKEN_TTL = 15 * 60`, which is already in seconds. Line 22 then multiplies it by 60 again:

    return now - token.created_at > TOKEN_TTL * 60

That makes the effective lifetime 54,000 seconds, or 15 hours. I ran it with a token created at t=0:

- 16 minutes: not expired
- 60 minutes: not expired
- 900 minutes (15 hours): not expired
- 901 minutes: expired

A token that should be dead after 15 minutes stays redeemable for 60 times longer than the changelog says. For a password reset token, that is a security-relevant gap.

**Why the tests didn't catch it**

I ran `pytest` and both tests pass, so the bug is hidden by the test design, not absent.

- `test_fresh_token_is_valid` checks a token at 60 seconds old. That passes under either 15 minutes or 15 hours.
- `test_old_token_is_rejected` checks a token at 2 days old. That is rejected under either value too.

Neither test probes anywhere near the boundary. So "Covered by `tests/test_auth.py`" is also not supported. The tests show that very old tokens are rejected and brand-new ones are accepted. They don't show a 15-minute limit. I did not mutate the code to see whether the tests notice a change, but the numbers above make it clear they can't tell 15 minutes from 15 hours.

**Fix**

1. In `auth.py`, drop the extra multiplier: `return now - token.created_at > TOKEN_TTL`.
2. Add boundary tests in `tests/test_auth.py`, for example:
   - a token at `TOKEN_TTL - 1` seconds is valid and redeems
   - a token at `TOKEN_TTL + 1` seconds is expired and `redeem` raises `PermissionError`
   - a token at 16 minutes (960 s) is rejected. This one fails on the current code, which confirms the test can catch the bug.

   Run the new tests against the current code first and confirm the 16-minute one fails, then fix and confirm it passes.

Once that is done, the changelog line is true as written, and I would move it to Supported. I can re-review quickly when you have the change.
