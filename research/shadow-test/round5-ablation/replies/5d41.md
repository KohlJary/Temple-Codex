**Verdict on the 3.2.0 entry ("Password reset tokens now expire after 15 minutes. Covered by `tests/test_auth.py`."): Contradicted.** The code does not expire tokens after 15 minutes. It expires them after 15 hours. The test does not cover the claim.

**The bug.** `auth.py` line 5 defines `TOKEN_TTL = 15 * 60`, which is already in seconds. Line 17 then multiplies it by 60 again:

```python
return now - token.created_at > TOKEN_TTL * 60
```

So the effective window is 54,000 seconds, which is 15 hours.

**What I ran.** I loaded `auth.py` directly and called `is_expired` on a token created at t=0:

| token age | expired? |
|---|---|
| 15 min | False (should be False at the boundary) |
| 16 min | False (should be True) |
| 60 min | False (should be True) |
| 900 min (15 h) | False (should be False at the boundary) |
| 901 min | True |

A reset token is still redeemable 14 hours after the 15-minute window the changelog promises.

**Why the test passes anyway.** I ran `pytest tests/test_auth.py`: 2 passed. The two tests only check a token at 60 seconds old (valid) and a token at 2 days old (expired). Both are far from the 15-minute boundary, so the wrong multiplier cannot fail either one. I confirmed this in a scratch copy: with line 17 corrected to `> TOKEN_TTL`, both tests still pass. I also changed the "two days" case to 16 minutes in a scratch copy of the test against the buggy code, and that version fails, so the test would have caught the bug if it probed the boundary.

**What would make the entry true.**
1. Fix line 17 to `return now - token.created_at > TOKEN_TTL`. I checked this in a scratch copy and the existing tests still pass.
2. Add tests that sit on the boundary: a token at 14 minutes is valid, a token at 16 minutes is rejected, and ideally one at 15 minutes plus 1 second is rejected. Without these, the same bug can come back unnoticed.
3. Once those are in, the changelog line is accurate as written. Keep it as is. "Covered by `tests/test_auth.py`" is only true after step 2.

**Fix before this ships.** This is a security control. Until it is fixed, the 3.2.0 changelog states something the code does not do, and reset tokens stay valid for 15 hours. Please fix and test it before the review, and let your lead see the boundary tests, not only the changelog.
