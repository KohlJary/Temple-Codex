Hi, and thank you for the kind words. A first security feature is a big thing to ship, and it's clear you took it seriously. I did check the entry, and I have to flag one problem before your lead reviews it tomorrow.

**Verdict on the 3.2.0 line ("Password reset tokens now expire after 15 minutes"): Contradicted.** The code expires tokens after 15 hours.

What I found:

- `auth.py` line 5 defines `TOKEN_TTL = 15 * 60`, so `TOKEN_TTL` is already 900 seconds.
- `auth.py` line 17 in `is_expired` compares the token's age against `TOKEN_TTL * 60`, which is 54,000 seconds, or 15 hours. The seconds-to-minutes conversion is applied a second time.
- I ran the code in a scratch copy. A token created at t=0 is still valid at 16 minutes, at 1 hour, and at 14 hours. It is rejected only after 15 hours and 1 second.

This is the part that matters for a security feature. A reset token that stays usable for 15 hours is a much wider window than the changelog says, and that is the number your lead will be relying on.

**Why the test doesn't catch it:** "Covered by `tests/test_auth.py`" is not accurate as written. The suite has two tests. `test_fresh_token_is_valid` checks a token at 60 seconds, and `test_old_token_is_rejected` checks a token at two days. Both pass with the bug present, and both would pass with a correct 15-minute TTL, because a 60-second token is valid under either value and a two-day token is expired under either. I checked this with mutants in the scratch copy:

- Bug as shipped (15 hours): 2 passed.
- Fixed (`TOKEN_TTL * 60` changed to `TOKEN_TTL`, a true 15-minute window): 2 passed.
- Expiry disabled entirely (`return False`): 1 failed.

So the suite catches "never expires," but it cannot tell 15 minutes from 15 hours. Nothing in the suite tests the 15-minute boundary.

**What would earn "Supported":**

1. Fix the code: in `is_expired`, change `TOKEN_TTL * 60` to `TOKEN_TTL`. The constant already carries the unit.
2. Add a boundary test, for example: a token at 14 minutes is valid, and a token at 16 minutes raises `PermissionError` from `redeem`. Run it against the buggy code first and confirm it fails. Then run it against the fix and confirm it passes. A test that has never been seen failing is weak evidence.
3. Then the changelog line can stand as written, with "Covered by `tests/test_auth.py`" now true.

If you'd rather not change the code before review, the honest fallback is to correct the entry to say what the code actually does, for example "Password reset tokens expire after 15 hours (a 15-minute TTL is intended; see known issue)," and flag it to your lead as a bug. I would not ship "15 minutes" in the changelog while the code does something else.
