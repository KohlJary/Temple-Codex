Hi! Thanks for the kind words, and good luck tomorrow. I'm glad you asked for a review before your lead sees it, because there is one significant problem in the 3.2.0 entry. It is a quick fix.

## Claim examined

CHANGELOG.md, 3.2.0: "Password reset tokens now expire after 15 minutes. Covered by `tests/test_auth.py`."

Narrow, testable form: a reset token whose age is more than 15 minutes is rejected by `redeem`, and the tests cover that.

## Finding 1: Falsifying. Tokens actually expire after 15 hours.

- **Claim as stated:** "expire after 15 minutes" (CHANGELOG.md, 3.2.0).
- **What I did:** Read `auth.py`, then ran `is_expired` on a token created at t=0 at several ages.
- **What happened:**
  - `auth.py` line 5 is `TOKEN_TTL = 15 * 60  # 15 minutes, in seconds`.
  - `auth.py` line 17 is `return now - token.created_at > TOKEN_TTL * 60`. That multiplies seconds by 60 again.
  - Output of my run:
    ```
    16 min expired? False
    60 min expired? False
    840 min expired? False
    899 min expired? False
    901 min expired? True
    15.0 hours effective
    ```
  - A token 16 minutes old, and one 14 hours old, are both accepted. The cutoff is at 900 minutes.
- **Why it matters:** This is a security feature. The changelog tells readers the exposure window is 15 minutes, and it is 60 times longer. A leaked reset link would stay usable for most of a day. Anyone reviewing or relying on the changelog would believe something false.
- **Fix (not applied; I did not touch your code):** change line 17 to `> TOKEN_TTL`. The unit is already seconds.
- **Re-check after the fix:** the 16-minute case should print `True`, the 14-minute case `False`. I would withdraw the finding on that observation.

## Finding 2: Gap. The tests cannot see this bug, so "Covered by tests/test_auth.py" overreaches.

- **Claim as stated:** "Covered by `tests/test_auth.py`."
- **What I did:** Read the tests and ran them: `2 passed`. They pass with the bug present.
- **What happened:** The only expiry test uses a token that is 2 days old. That is expired under both the 15-minute and 15-hour readings, so it cannot tell them apart. The other test uses 60 seconds old, which is valid under both. Nothing tests a age between 15 minutes and 15 hours, or the boundary itself.
- **Why it matters:** A reader sees "covered" and a green run and assumes the 15-minute number was checked. It was not.
- **Narrower true sentence today:** "Tokens are rejected after some bounded time. Tests check a 1-minute token is valid and a 2-day token is rejected."
- **Test that closes it:** add checks at the boundary, for example `is_expired(t, now=created_at + 15*60)` is False, `+ 15*60 + 1` is True, and `+ 16*60` is True. The last one fails today, which is the point: it would have caught this bug. Please run it against the buggy line to confirm that it fails before you fix it.

## What held up

- The constant `TOKEN_TTL = 15 * 60` is correct as 900 seconds.
- `redeem` raises `PermissionError` when `is_expired` is true and returns `user_id` otherwise. I read it and ran it through the existing tests.
- The existing two tests pass (`2 passed`), and the 2-day rejection and 1-minute acceptance behave as the tests state.
- Tokens use `secrets.token_urlsafe(32)`, which is a sound source of randomness. I read this but did not assess the rest of the feature's security design.

## What I did not check

I only looked at these three files. I did not check where tokens are stored or issued, whether they are single-use, or the rate limiting. The changelog does not claim those things, so I mention them only so my silence is not read as approval.

## Verdicts

- "Password reset tokens now expire after 15 minutes": **Unsupported.** Measured expiry is 15 hours.
- "Covered by `tests/test_auth.py`": **Supported, narrower.** The tests cover a 1-minute-valid and a 2-day-rejected token. They do not cover the 15-minute limit.

Fixing the one-line multiplier and adding the boundary test should make both claims true, and that is a small change before tomorrow's review.
