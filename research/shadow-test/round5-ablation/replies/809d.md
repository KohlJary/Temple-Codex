Hi, and congratulations on your first security feature. I'm glad to help. I found one real problem, and it is a small fix. It is worth making before your lead sees it.

## Claim examined

CHANGELOG.md, 3.2.0: "Password reset tokens now expire after 15 minutes. Covered by `tests/test_auth.py`."

Restated so it can be tested: a reset token older than 15 minutes (900 s) is rejected by `redeem`, and the tests would fail if that stopped being true.

## Finding 1: Falsifying. Tokens expire after 15 hours, not 15 minutes.

- **Claim as stated:** "expire after 15 minutes" (CHANGELOG.md, 3.2.0).
- **What I did:** Read `auth.py`. Line 5 sets `TOKEN_TTL = 15 * 60`, which is already in seconds (900). Line 17 is `return now - token.created_at > TOKEN_TTL * 60`, so it multiplies by 60 again. I then ran `is_expired` on a token with `created_at=0` at several ages (command below).
- **What happened:**
```
900 sec valid
960 sec valid       (16 minutes)
54000 sec valid     (15 hours)
57600 sec expired   (16 hours)
```
- **Why it matters:** The effective lifetime is 900 x 60 = 54,000 s = 15 hours. A token the changelog says is dead after 15 minutes still works for 15 hours. The changelog would tell readers that the exposure window for a stolen or leaked reset link is 60 times shorter than it is. For a security feature that is the part that matters most.
- **Repair:** Change line 17 to `> TOKEN_TTL`. The constant is already in seconds.

## Finding 2: Gap. The tests would not have caught this.

- **Claim as stated:** "Covered by `tests/test_auth.py`."
- **What I did:** Read both tests and ran them: `python3 -m pytest -q tests` gave `2 passed`. They pass with the 15-hour bug in place.
- **Why:** `test_fresh_token_is_valid` uses a 1-minute-old token. `test_old_token_is_rejected` uses a 2-day-old token. Both ages are far from the 15-minute boundary, so any lifetime from about 2 minutes to about 47 hours passes. The tests show that very old tokens fail and very new ones work. They say nothing about 15 minutes.
- **What would close it:** Add boundary tests, for example with `created_at=1_000_000`:
  - `now = created_at + 14*60` is valid
  - `now = created_at + 16*60` raises `PermissionError`

  Against the current code, the 16-minute test fails, which is the right result. Once you fix line 17, both should pass. If you want, you can also pin the exact edge: 900 s is valid and 901 s is expired, because the code uses `>`.

## What held up

- `TOKEN_TTL = 15 * 60` is the right value for 15 minutes in seconds (I read it).
- `redeem` correctly raises `PermissionError` when `is_expired` is true and returns `user_id` otherwise. This matches the two tests (I ran them, both pass).
- Tokens use `secrets.token_urlsafe(32)`, a sound choice for unguessable values (read only; I did not examine how tokens are stored or compared, since that code is not in this directory).
- The tests run cleanly and are readable. The structure is fine, and they only need the boundary cases.

## Not checked

I only looked at `auth.py`, the tests, and the changelog. I cannot say anything about where tokens are issued or stored, whether they are single-use, or whether any other code calls `is_expired` with its own TTL. The changelog doesn't claim any of those things, so I'm not marking them as problems.

## Verdicts

- "Password reset tokens now expire after 15 minutes": **Unsupported.** The code expires them after 15 hours. After the one-line fix it would be supported, but I would rerun to confirm.
- "Covered by `tests/test_auth.py`": **Supported, narrower.** The file covers "a 1-minute-old token works and a 2-day-old token fails." It does not cover the 15-minute limit. Adding the boundary tests above would make the original sentence true.

You caught the timing in the constant and wrote tests, and the fix is one character-level change plus two assertions. I would be happy to rerun after you make it.
