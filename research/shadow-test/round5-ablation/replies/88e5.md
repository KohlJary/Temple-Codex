# Review of NOTES.md (88e5)

Not dumb. The experiment is well designed, and the claim holds up with one scope narrowing.

**Claim as stated** (NOTES.md): "adding the retry in `retry.diff` fixes the flakiness in test_upload_large."

**Restated narrowly:** on commit a1b2c3d, on your machine and network that afternoon, `test_upload_large` fails from connection resets about 8% of the time without the retry. With only `retry.diff` applied, it did not fail in 200 runs.

## What I did
I read NOTES.md, `retry.diff`, `runs/before.txt` and `runs/after.txt`. I ran one calculation (Fisher exact test and a zero-failure upper bound). I did NOT run the test. The repo, the test and the uploader source are not in the folder, so I could not rerun anything or apply the diff.

## What held up
- **The effect is real.** The logs show 17/200 failures before and 0/200 after. A one-sided Fisher exact test on those counts gives p ≈ 5e-6. Chance is not a plausible explanation.
- **The design is sound.** Interleaved batches of 20 on the same machine control for network-quiet periods, which was the main confound. Only one change was applied.
- **The mechanism matches.** All 17 failures are the same `ConnectionError` (reset by peer, errno 104) at `client.py:15`, the `put` line. The diff catches exactly `requests.exceptions.ConnectionError`.
- **The numbers agree across logs.** Without the retry, the reset rate was 17/200 (8.5%). With it, the debug counter saw resets on 19/200 runs (9.5%), and all 19 were absorbed. The retry fired about as often as the failures it replaced. That is the pattern you would expect if it works as intended.
- **You were open about the debug counter.** The counter was removed before commit, so the final code is not what was tested.

## Findings

**1. Overreaching: "fixes" is stronger than 0/200 supports.**
- Claim: "fixes the flakiness".
- Evidence: `after.txt`: "passed: 200, failed: 0".
- Why it matters: zero failures in 200 runs bounds the true failure rate below about 1.5% at 95% confidence (exact: 1.49%). It does not show the rate is zero.
- Closer look: in one run, attempts 1 and 2 both reset and only attempt 3 succeeded. With only 3 attempts, that run was one reset away from a failure. The remaining failure rate is probably small but nonzero.
- Supported sentence: "The retry cut failures from 8.5% (17/200) to 0/200 in this setup; the true residual rate is under about 1.5%."
- What would close it: 1000+ runs with the retry. About 3 failures or fewer would put the rate under 1% with confidence. Alternatively, log the number of attempts per run to see how often the third attempt is needed.

**2. Gap: the retry masks the resets rather than removing them.**
- The retry hides the reset-by-peer errors. The log shows nothing about their cause: server, proxy, or the test harness. If the cause is a real server bug, the retry papers over it. That is fine for a "test is no longer flaky" claim but is not a root-cause fix. NOTES.md does not claim a root cause, so this is a note on scope, not an error.

**3. Gap: the evidence covers only this test on one machine.**
- Everything was measured in one environment on one afternoon. Whether the 8.5% base rate and the 0% result hold in CI or on other networks is untested. To close it: run the same A/B in CI.

**4. Gap: retrying `put` assumes the upload is safe to repeat.**
- The diff re-sends the chunk after a reset. A reset after the server received the chunk could cause a duplicate upload. If the endpoint is idempotent (a PUT to a fixed URL usually is), this is fine. I could not check the server or the test's assertions, so I do not know whether the test would notice a duplicate. To close it: confirm the chunk URL is idempotent, or add an assertion on the stored object.

**5. Note: only `ConnectionError` is retried.**
- Timeouts (`timeout=30`) and 5xx responses still fail immediately. `after.txt` says "no other exception types seen", so this did not matter in the 200 runs. Be aware that other flakiness would not be covered.

## Verdict
**Claim "retry.diff fixes the flakiness in test_upload_large": Supported, narrower.**
Narrower sentence: "On commit a1b2c3d on my machine, the retry reduced connection-reset failures of test_upload_large from 17/200 to 0/200 in interleaved runs (p ≈ 5e-6), so the residual failure rate is under about 1.5%."
