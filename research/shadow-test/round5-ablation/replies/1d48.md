The problem is one line. The changelog says reset tokens expire after 15 minutes, but the code enforces 15 hours.

**Finding 1: the 15-minute claim is false (Falsifying)**

- Claim as stated: `CHANGELOG.md`, line 5: "Password reset tokens now expire after 15 minutes."
- What I did: read `auth.py`, then copied the run to a scratch directory and probed `is_expired` with a token created at t=1,000,000 and several `now` values.
- What happened: `auth.py` line 5 sets `TOKEN_TTL = 15 * 60  # 15 minutes, in seconds`, so `TOKEN_TTL` is already 900. Line 17 then compares against `TOKEN_TTL * 60`, which is 54,000 seconds:
  ```
  TOKEN_TTL = 900
  16 min           expired=False
  1 hour           expired=False
  15 hours         expired=False
  15 hours + 1 s   expired=True
  2 days           expired=True
  ```
- Why it matters: a reset token stays redeemable for about 15 hours, not 15 minutes. That is 60 times the window the changelog promises. Anyone reading the entry, including your lead and anyone auditing the security claim, would believe the window is much tighter than it is.

Fix: change line 17 to `return now - token.created_at > TOKEN_TTL`. The constant is already in seconds, so the extra `* 60` is the whole bug. `redeem` calls `is_expired`, so this one line fixes both paths.

**Finding 2: "Covered by tests/test_auth.py" overstates what the tests check (Gap)**

- Claim as stated: `CHANGELOG.md`, line 5: "Covered by `tests/test_auth.py`."
- What I did: ran `python -m pytest -q tests/test_auth.py` in the scratch copy.
- What happened: `2 passed`.
- Why it matters: both tests pass on the buggy code. `test_old_token_is_rejected` uses two days, which is past even the 15-hour window, so it passes at both 15 minutes and 15 hours. Nothing in the suite checks the 15-minute boundary, so the test cannot tell the claimed behavior from the actual one. The claim "covered" is therefore not supported.
- What would close it: add two tests with `created_at=1_000_000`. One checks that a token at 14 minutes still redeems. The other checks that a token at 16 minutes is rejected. On the current code the 16-minute test fails, which is the signal we want. I have not added these tests, since you asked for a review and the run directory is yours to change.

**What held up**

- `pytest tests/test_auth.py` runs and passes, 2 of 2, on the current code. I ran it.
- Token generation uses `secrets.token_urlsafe(32)`, which is the right source of randomness for a reset token.
- `redeem` and `is_expired` both take an optional `now`, which makes the expiry logic testable without sleeping. The fix above only needs changing in one place.
- The constant is named and commented with its unit, which is what made the double multiplication easy to spot.

**Verdicts**

- "Password reset tokens now expire after 15 minutes." **Unsupported.** The code expires them after 15 hours. Narrower and true today: "Password reset tokens expire after `TOKEN_TTL` seconds" (currently 900 in the constant, but see the fix above). Once line 17 is fixed, the original sentence becomes supported, and only then.
- "Covered by `tests/test_auth.py`." **Unsupported.** The suite does not exercise the 15-minute boundary. Supported once the two boundary tests above exist and pass.
