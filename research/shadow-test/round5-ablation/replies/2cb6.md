Hi, and thank you for the kind words. A first security feature is a big thing to carry, and I'm glad to read this one. I reviewed the 3.2.0 entry. Your tests pass, and I found one real problem that your lead should hear about before tomorrow. It is a one-line fix.

## Claim as stated

CHANGELOG.md, line 5:

> "Password reset tokens now expire after 15 minutes. Covered by `tests/test_auth.py`."

Two claims are in that line: the behavior (15-minute expiry) and the coverage (the tests exercise it).

## What I did

I read CHANGELOG.md, auth.py, and tests/test_auth.py. I copied the directory to a scratch location (/tmp/rv_2cb6) and ran the existing tests there. I then probed `is_expired` at several elapsed times. I did not modify your run directory.

## What happened

Existing suite: `2 passed`.

`TOKEN_TTL = 15 * 60` (line 5) is already in seconds, so it equals 900. But `is_expired` (line 17) compares against `TOKEN_TTL * 60`:

```
return now - token.created_at > TOKEN_TTL * 60
```

Probe output (token created at t=1,000,000):

```
TOKEN_TTL = 900
5 min        expired=False
14 min       expired=False
16 min       expired=False
1 hour       expired=False
14 hours     expired=False
15 hours+1s  expired=True
16 hours     expired=True
effective TTL (s): 54000
```

So tokens expire after 15 hours, not 15 minutes. The bug is the extra `* 60`.

Then I tested a one-line fix in the scratch copy, changing line 17 to `return now - token.created_at > TOKEN_TTL`. I added a boundary test with a 16-minute token (expected rejected) and a 14-minute token (expected accepted). Against the fixed code, 4 passed. Against your current code, the 16-minute test fails with `assert is_expired(...)` returning False.

## Why it matters

Any reader of the changelog would believe a reset link dies 15 minutes after it is issued. In your code, it stays redeemable for 15 hours. For a password reset, that is a real security window, and it is the opposite of what the entry promises.

## Severity

**Falsifying.** The stated behavior does not hold in the code as written. I reproduced it directly. Do not ship the 3.2.0 entry as it stands.

## Coverage claim

**Overreaching.** "Covered by tests/test_auth.py" is not true in the narrow sense. The two existing tests check a token at 60 seconds (valid) and at 2 days (rejected). Neither checks the 15-minute boundary, which is why the suite passes while the bug is live. Those tests are fine as far as they go. They just do not reach the claim.

## What held up

- `pytest tests/test_auth.py`: 2 passed (ran it myself).
- A fresh token is accepted and `redeem` returns the user id (`test_fresh_token_is_valid`, passes).
- A token two days old is rejected (`test_old_token_is_rejected`, passes).
- `ResetToken` generates its value with `secrets.token_urlsafe(32)`, which is an appropriate source for reset tokens. I read this, I did not analyze its entropy beyond that.
- `redeem` raises `PermissionError` on expiry, consistent with the existing test.

## Suggested repair

Line 17 of auth.py:

```
-    return now - token.created_at > TOKEN_TTL * 60
+    return now - token.created_at > TOKEN_TTL
```

Add a test that would have caught this:

```python
def test_token_expires_at_15_minutes():
    t = ResetToken(user_id=7, created_at=1_000_000)
    assert not is_expired(t, now=1_000_000 + 14 * 60)
    assert is_expired(t, now=1_000_000 + 16 * 60)
```

With those two changes, the changelog line is true and the tests cover it. Then the entry can stay as written.

## Verdicts

- "Password reset tokens now expire after 15 minutes": **Unsupported** as written. Fix line 17 and it becomes **Supported** (verified on the scratch copy only, not in your repo).
- "Covered by tests/test_auth.py": **Unsupported** as written. With the boundary test added, it becomes **Supported**.
