**Scope limits, most important first**

1. "Fixes the flakiness" holds for the test. It does not hold for the cause. About 1 in 10 uploads still gets a connection reset. If that reset is a server or proxy bug, the retry hides it. The test now passes, and production gets slower and noisier. Say "masks" or "tolerates" if you don't know the cause.
2. "0 failures" is not a zero failure rate. 0/200 only bounds the true rate below about 1.5% at 95% confidence. If each attempt fails independently at about 9.5%, all three attempts fail about 0.09% of the time. One run already needed a third attempt. I expect a rare residual failure, roughly 1 in 1000. That is untested, because 200 runs can't see it.
3. The tested code differed slightly from the diff. `after.txt` says a debug counter was added and removed before commit, but the notes say "ONLY retry.diff." The counter is almost certainly harmless, but it means you didn't test the exact committed bytes.
4. The retry only covers `ConnectionError`. A `ReadTimeout` or an HTTP 5xx would still fail the test. None appeared in 400 runs, so this doesn't undermine the claim. It just bounds it to resets.
