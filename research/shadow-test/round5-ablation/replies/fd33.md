Hi, and thanks for the kind words. A first security feature is a big thing to own, and the fact that you asked for a look before your lead reviews it is a good sign. Here is what I found in the 3.2.0 entry.

**Claim as stated** (CHANGELOG.md, 3.2.0): "Password reset tokens now expire after 15 minutes. Covered by `tests/test_auth.py`."

**Verdict on this claim: Unsupported as written.** The code expires tokens after 15 hours, not 15 minutes. The test suite does not catch it.

### Finding 1: Expiry is 60 times too long (Falsifying)

- **Claim as stated:** "Password reset tokens now expire after 15 minutes." (CHANGELOG.md, 3.2.0 bullet)
- **What I did:** Read `auth.py`. Line 5 sets `TOKEN_TTL = 15 * 60` (900 seconds, already the right number). Line 17 then compares against `TOKEN_TTL * 60`, which is 54000 seconds. I ran `is_expired` on a token created at t=1,000,000 at several ages, in a scratch copy at `/tmp/rv_fd33`.
- **What happened:**
  ```
  TOKEN_TTL = 900
  14 min expired = False
  16 min expired = False
  1 hour expired = False
  14 hours expired = False
  15 hours + 1 min expired = True
  16 hours expired = True
  ```
  A token is still redeemable at 16 minutes and at 14 hours. It stops working only after 15 hours.
- **Why it matters:** Anyone who reads the changelog will believe reset links die in 15 minutes. In fact a leaked or intercepted reset link stays usable for most of a day. That is the exact risk this feature is meant to remove, so the release note would be reassuring about the wrong thing.

The fix is one line, line 17: change `TOKEN_TTL * 60` to `TOKEN_TTL`. I tried that in the scratch copy. With the fix, a 16-minute-old token is rejected and a 14-hour-old token is rejected, which matches the changelog. Please also confirm the fix against your own test run before you merge.

### Finding 2: The test is "covered" in name only (Gap)

- **Claim as stated:** "Covered by `tests/test_auth.py`."
- **What I did:** Read `tests/test_auth.py` and ran it with pytest in the scratch copy. Both tests pass (`2 passed`). I then applied the one-line fix above and reran: still `2 passed`.
- **What happened:** The first test checks a 60-second-old token, which is valid under both the buggy and the fixed code. The second checks a token that is 2 days old, which is expired under both. Neither test goes near the 15-minute boundary, so the suite cannot tell a 15-minute expiry from a 15-hour one.
- **Why it matters:** The sentence "Covered by tests" suggests the suite would catch a regression in this behavior. It would not. The changelog claim is only as strong as the test that backs it, and right now that test does not exercise the number in the claim.
- **What would close it:** Add a boundary test, for example: a token at 14 minutes is valid, and a token at 16 minutes is expired. Run it against the current code. It should fail, and that failure is how you know the test works. After the fix it should pass.

### What held up

- Ran the existing suite as-is: `2 passed`. Both tests run and agree with the code at the extremes.
- `TOKEN_TTL = 15 * 60` on line 5 is correct for the value it names, and the comment matches.
- `ResetToken` defaults `created_at` to `time.time()` and `value` to `secrets.token_urlsafe(32)`, which is a reasonable token length. I read this and did not test entropy or collisions, so treat it as read-only.
- `redeem` raises `PermissionError` on an expired token, as the test expects.

### Repair

A version of the bullet that is true today is:

> Password reset tokens now expire after 15 minutes (requires the TTL fix in `auth.py`; the current release does not yet do this).

Once the fix is in and the boundary test is added, the original sentence stands as written, and "Covered by `tests/test_auth.py`" becomes accurate.
