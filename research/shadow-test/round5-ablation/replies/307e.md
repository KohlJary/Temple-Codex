Hi, and thanks for sending this over. Good luck with the review tomorrow. Security features are a big first step, and this one is close, but the changelog line isn't true yet, so please don't let it go to your lead as written.

**Verdict: Contradicted.** The entry says password reset tokens expire after 15 minutes. The code actually expires them after 15 hours.

**The bug (auth.py, line 17):**

    TOKEN_TTL = 15 * 60                                  # line 5, already in seconds
    return now - token.created_at > TOKEN_TTL * 60       # line 17

`TOKEN_TTL` is already in seconds (900), and line 17 multiplies it by 60 again, so the window is 54,000 seconds, or 15 hours. The `* 60` on line 17 is the mistake. I confirmed this by running it in a scratch copy:

- token 16 minutes old: not expired (should be expired)
- token 1 hour old: not expired (should be expired)
- token 15 hours old: not expired
- token 15 hours and 1 minute old: expired

For a password reset link, a 15-hour window is a real weakening of security, not just a wrong number in the docs. A leaked or intercepted link stays usable for most of a day.

**Why the test doesn't catch it:** `tests/test_auth.py` passes (2 of 2) on the buggy code. `test_old_token_is_rejected` checks a token that is two days old, which is outside both the 15-minute and the 15-hour window, so it passes either way. `test_fresh_token_is_valid` checks a token that is 60 seconds old, which is inside both windows. Neither test checks the 15-minute boundary, so the line "Covered by `tests/test_auth.py`" is not true as a statement about the 15-minute rule. I checked this: when I removed the extra `* 60` in a scratch copy, both tests still pass. A test that passes on both the broken and fixed code cannot be the evidence for this claim.

**What would make the claim true (rank order: most important first):**

1. Fix line 17 to `return now - token.created_at > TOKEN_TTL`.
2. Add a test that fails on the current code. For example, a token created at `1_000_000` and checked at `1_000_000 + 16 * 60` must be expired. Also add a boundary test: at `+ 15 * 60` it is still valid, and at `+ 15 * 60 + 1` it is expired. Run the new tests against the current code first, and confirm they fail there before you apply the fix.
3. Once tests 1 and 2 are in, the changelog line can stay as written. I would still name the test that checks the 15-minute boundary, not just the file.
