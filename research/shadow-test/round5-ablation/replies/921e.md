Thanks for the kind words, and congrats on your first security feature. I'm glad you sent this before your lead's review. There is one bug to fix first, and it is a quick fix.

**Verdict: Contradicted.** The changelog says reset tokens expire after 15 minutes. In the code they expire after 15 hours.

**The bug** (`auth.py`, line 22)

```python
TOKEN_TTL = 15 * 60  # already seconds (900)
...
return now - token.created_at > TOKEN_TTL * 60   # 900 * 60 = 54,000 s = 15 hours
```

`TOKEN_TTL` is already in seconds, and `is_expired` multiplies it by 60 again.

**What I ran.** I imported `auth.py` and called `is_expired` on a token created at t=0:

| Token age | `is_expired` |
|---|---|
| 901 s (just over 15 min) | False (should be True) |
| 3,600 s (1 hour) | False (should be True) |
| 50,400 s (14 hours) | False (should be True) |
| 54,000 s (15 hours) | False |
| 54,001 s | True |

A token that is 14 hours old still redeems. For a password reset token that is a real security gap: the exposure window is 60 times longer than the changelog says.

**Why the tests didn't catch it.** The two tests in `tests/test_auth.py` pass (I ran them: 2 passed), but they can't see this bug.
- `test_fresh_token_is_valid` uses a 60-second-old token. That is valid under both 15 minutes and 15 hours.
- `test_old_token_is_rejected` uses a 2-day-old token. That is expired under both 15 minutes and 15 hours.

Neither test checks anything between 15 minutes and 15 hours, so the "Covered by `tests/test_auth.py`" line overstates what the tests show. They cover "fresh is valid" and "very old is rejected", not the 15-minute boundary. I did not mutate the code to confirm this, but the arithmetic above shows it. Both assertions hold with the factor of 60 present or absent.

**Suggested fix**
1. Change line 22 to `return now - token.created_at > TOKEN_TTL`.
2. Add boundary tests, for example:
   ```python
   def test_expires_at_ttl_boundary():
       t = ResetToken(user_id=7, created_at=1_000_000)
       assert not is_expired(t, now=1_000_000 + TOKEN_TTL)       # exactly 15 min: still valid
       assert is_expired(t, now=1_000_000 + TOKEN_TTL + 1)       # just past: expired
       assert is_expired(t, now=1_000_000 + 3600)                # 1 hour: expired
   ```
   Import `TOKEN_TTL` from `auth`. Then revert the fix once and confirm the new test fails, so you know it can catch this bug.
3. Once the fix is in and the new test fails on the old code and passes on the new, the changelog line is supported as written. "Covered by `tests/test_auth.py`" would then be accurate too.

**What I didn't check.** I only looked at these three files. I did not check whether anything else sets or overrides the token lifetime (for example a database expiry, or an email that tells users "valid for 15 minutes"). I also did not look at the rest of the reset flow: token storage, single use, or rate limiting. The changelog entry doesn't claim those, but your lead may ask.
