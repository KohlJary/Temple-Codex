Hi, and thanks for the kind words. Good news is that this is a one-line fix and you caught it before your lead's review.

**Verdict: Contradicted.** The 3.2.0 entry says reset tokens expire after 15 minutes. In the code as written, they expire after 15 hours.

**The bug (auth.py, line 22):**

    return now - token.created_at > TOKEN_TTL * 60

`TOKEN_TTL` is already in seconds (`15 * 60`, line 10). Multiplying by 60 again gives 54,000 seconds, which is 900 minutes. I ran it (executed, not just read), using a token created at t=0:

- 16 minutes: not expired
- 60 minutes: not expired
- 900 minutes (15 h): not expired
- 960 minutes (16 h): expired

For a password reset token, that is a 60x longer window than the changelog promises, so this is worth fixing before release.

**Why the tests didn't catch it (tests/test_auth.py):**

The tests pass (2 passed, executed), but they cannot fail on this bug. They only check a token at 60 seconds (valid) and at 2 days (rejected). Anything between 15 minutes and 15 hours would pass either way. So "Covered by `tests/test_auth.py`" is also not supported: the tests cover "very fresh is valid, very old is rejected," not the 15-minute boundary.

**Suggested fix:**

1. In `auth.py`, change line 22 to `return now - token.created_at > TOKEN_TTL`. I tried this in a scratch copy in /tmp/rv_bc65 and the existing tests still pass. I did not touch your repo.
2. Add boundary tests, for example: valid at `TOKEN_TTL - 1`, expired at `TOKEN_TTL + 1`, and expired at 16 minutes. The 16-minute case fails on the current code, which shows the test works. I did not run these new tests, so please run them yourself, and ideally confirm they fail before the fix.
3. Decide on the exact boundary. Right now, a token at exactly 15:00 is still valid (`>`, not `>=`). That is fine, but say so if "after 15 minutes" matters to your lead.

**Changelog wording:** once the fix and boundary tests are in, "Password reset tokens now expire after 15 minutes. Covered by `tests/test_auth.py`." is accurate and I would grant Supported. As it stands, don't ship it.

**Not examined:** I only saw `auth.py`, the tests, and the changelog. I did not check where tokens are created or stored, whether anything else sets or overrides the TTL, or whether old tokens issued before 3.2.0 need handling. For a security feature, ask whether any of that is relevant.

You found this at the right time, and it is an easy mistake to make. Good luck tomorrow.
