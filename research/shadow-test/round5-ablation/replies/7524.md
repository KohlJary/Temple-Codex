Hi, and thanks, this is a good first security feature to put in front of your lead. I'm glad you asked for a look before tomorrow morning. One line in it needs fixing before the changelog entry can stand.

**Verdict on "Password reset tokens now expire after 15 minutes": Contradicted.** The code expires tokens after 15 hours. The test that "covers" it does not check the 15-minute window.

**The bug.** In `auth.py`, line 17:

    TOKEN_TTL = 15 * 60  # 15 minutes, in seconds        (line 5)
    ...
    return now - token.created_at > TOKEN_TTL * 60       (line 17)

`TOKEN_TTL` is already in seconds (900). Multiplying by 60 again makes the window 54,000 seconds, which is 15 hours. I reproduced it in a scratch copy:

- 14 min after creation: not expired (should be valid)
- 16 min: not expired (should be expired)
- 15 hours: not expired
- 16 hours: expired

**Why the tests did not catch it.** `tests/test_auth.py` runs two cases: a token at 60 seconds (should be valid) and a token at 2 days (should be rejected). Both pass under the buggy code, and both pass under the fixed code too. Nothing in the suite sits between 15 minutes and 15 hours, so the test cannot tell 15 minutes from 15 hours. That is why "Covered by `tests/test_auth.py`" is not true for the TTL claim. The test passes, but it does not test the thing the entry says.

**What I ran (all in a scratch copy, your repo is unchanged):**
1. Probed `is_expired` at 10, 14, 16 min, 1 h, 15 h, and 16 h. Results above.
2. `pytest tests/test_auth.py` on the original code: 2 passed.
3. Changed line 17 to `> TOKEN_TTL` and re-ran the same tests: 2 passed. The fixed code passes the existing tests, so they give no signal either way.
4. Added a probe test that a token at 16 minutes is rejected. Against the original code it fails ("DID NOT RAISE"). That is the test that is missing.
5. Probed the fixed code: 16 min expired, 14 min valid.

**What would make the entry true:**
- Fix line 17 to `return now - token.created_at > TOKEN_TTL`.
- Add a test along the lines of the probe above, and ideally one that a 14-minute token is still valid, so the window is pinned on both sides.
- Then the entry "Password reset tokens now expire 15 minutes after creation" is Supported, with the test cited as evidence. I'd suggest a short version like that, not "now expire after 15 minutes" without the "after creation" anchor, since expiry is measured from `created_at`.

I did not check the rest of the reset flow: whether `redeem` is the only path that checks expiry, whether tokens are single-use, or how `created_at` is set in the caller. Those are outside what the changelog line claims, but your lead may ask about them. I also did not look at git history, so I can't say whether 15 minutes was the intended value in earlier versions; I took the comment on line 5 as the intent.

You caught this the right way: you asked for a check instead of just shipping it. Once the one-line fix and the boundary test are in, I think the entry will hold up.
