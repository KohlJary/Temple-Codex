Review of NOTES.md (runs/4df0): retry in retry.diff and test_upload_large

**Verdict on the claim: Supported, narrower.**

Narrower sentence the evidence carries: "On commit a1b2c3d, on one machine, the three-attempt retry on ConnectionError in retry.diff removed the connection-reset failures from test_upload_large: 0 of 200 runs failed with the retry, 17 of 200 without it (interleaved batches, two-sided Fisher exact p ~ 1e-5). The retry absorbs the resets. The logs do not show why the server resets connections."

## Findings

**1. Overreaching: "fixes the flakiness."**
- Claim as stated: NOTES.md, "adding the retry in `retry.diff` fixes the flakiness in test_upload_large."
- What I did: read retry.diff, runs/before.txt, runs/after.txt; computed the Fisher exact test on 17/200 vs 0/200.
- What happened: before.txt lists 17 failures, every one `ConnectionError ... Connection reset by peer`. after.txt reports 200 passed, 0 failed, and 19 retries, all ConnectionError.
- Why it matters: "fixes" reads as a root-cause fix. The evidence shows the retry masks the resets. A reader would think the server or network problem is gone. It is not shown to be gone.
- Severity: overreaching, because the data supports the mitigation but not the word "fixes."
- Repair: "The retry absorbs connection resets, which removed the test's failures on this machine (0/200 vs 17/200). The cause of the resets is not addressed."

**2. Gap: the 200-run "after" result is from an instrumented build.**
- Claim as stated: after.txt header, "commit a1b2c3d + retry.diff only."
- What I did: read after.txt.
- What happened: the retry log in the same file says "from added debug counter, removed before commit." So the 200 passing runs came from a build with a counter that is not in retry.diff.
- Why it matters: the counter is probably inert, but the pass count is for a different artifact than the one named.
- Severity: gap, because the claim is about the diff and the run tested a near-copy.
- Test that closes it: on a clean checkout of a1b2c3d with only retry.diff applied, run `pytest tests/test_upload.py::test_upload_large` 200 times, interleaved with the no-retry batches. Confirm with `git diff` that no counter is present.

**3. Gap: the retry resends `data`, and I cannot check its type.**
- Claim as stated: retry.diff calls `self.session.put(url, data=data, ...)` inside the retry loop.
- What I did: read retry.diff. The caller of `upload_chunk` is not in runs/, so the type of `data` is unknown.
- What happened: `CHUNK = 8 * 1024 * 1024` suggests bytes, but nothing confirms it. My scratch test (finding 5) shows the retry resends identical bytes, which says nothing about streams.
- Why it matters: if `data` is a generator or file handle, the retried attempt sends an empty or partial body. The test could still pass, or fail in a way the counter does not show.
- Severity: gap, because the code shown is only safe for re-readable data.
- Test that closes it: check the call site of `upload_chunk`. If `data` can be a file or iterator, add a test where the server records the full body received on a retried attempt, and compare its length with the chunk size.

**4. Gap: the scope is one machine and one afternoon.**
- Claim as stated: "fixes" applies to the test in general.
- What I did: checked the run counts only.
- What happened: 0/200 gives a 95% upper bound of about 1.5% failure rate (rule of three). That is not zero, and the sample has one network path.
- Why it matters: a different network or CI runner may reset connections at a different rate, or not at all.
- Test that closes it: inject resets deterministically (a local server that drops every Nth connection) and show the retry recovers every injected reset. Then run the test on CI.

**5. Question: the traceback line does not match the hunk.**
- Claim as stated: before.txt reports failures at `uploader/client.py:15 upload_chunk`.
- What I did: read the hunk header in retry.diff.
- What happened: the header `@@ -12,5 +13,11 @@` makes original line 12 blank, 13 the `def`, 14 the `session.put(...)` call, and 15 `raise_for_status()`. A ConnectionError from `put` should point at line 14.
- Why it matters: either the log came from a different version of client.py, or the line numbers are off by one. Both would weaken the link between the logs and this diff.
- Question: is the client.py used for the before/after runs the same file that retry.diff was made against?

## What held up

- The before and after runs share the commit label and the test command. They ran in 10 batches of 20, interleaved, so drift in network conditions falls on both sides. Matches NOTES.md's description of the method.
- before.txt is internally consistent: 183 passed + 17 failed = 200. I counted the 17 failure lines (runs 007, 019, 033, 041, 058, 066, 072, 090, 104, 111, 127, 138, 150, 163, 171, 186, 198). All are ConnectionError from the same call site. No other exception type appears.
- after.txt is internally consistent: 18 runs retried once and 1 run retried twice, total 19 retried runs. "No other exception types seen" fits the data.
- Mechanism matches data: the before-run failure rate (17/200 = 8.5%) is close to the after-run retry rate (19/200 = 9.5%). That fits the same underlying reset rate, with the retry recovering the runs that would have failed. This is the strongest part of the note.
- Fisher exact test on 17/200 vs 0/200: two-sided p ~ 1.1e-5. Computed by hypergeometric in scratch space (/tmp/rv_4df0). The difference between the two arms is not chance on these numbers.
- Retry logic: I copied the `upload_chunk` body from retry.diff verbatim into /tmp/rv_4df0/test_retry.py and ran 4 tests with a mocked session: recovers after two resets (3 calls); raises after three resets (3 calls); resends identical bytes on retry; does not retry an HTTPError (1 call). All 4 passed. This checks the logic only, not the real network or the uploader's data type.
