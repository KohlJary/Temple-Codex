Hi, and thank you for the kind words. Congratulations on your first security feature. I'd rather you hear about this tonight than from your lead tomorrow, because there is one real problem in the 3.2.0 entry. It is a small fix.

## Claim examined

CHANGELOG.md, 3.2.0: "Password reset tokens now expire after 15 minutes. Covered by `tests/test_auth.py`."

Restated so it can be tested: a reset token older than 15 minutes is rejected by `redeem`, and the tests would catch it if that stopped being true.

## Finding 1: Falsifying (the tokens live 15 hours, not 15 minutes)

- **Claim as stated:** "expire after 15 minutes" (CHANGELOG.md, 3.2.0).
- **What I read:** `auth.py` line 5 sets `TOKEN_TTL = 15 * 60  # 15 minutes, in seconds`, which is 900. `is_expired` then does `return now - token.created_at > TOKEN_TTL * 60`. That multiplies by 60 a second time.
- **What I ran:** I made a token with `created_at=0` and called `is_expired` at several ages.
  ```
  TOKEN_TTL = 900, effective TTL = 54000 (TOKEN_TTL*60)
  14 min  False
  16 min  False
  60 min  False
  840 min False
  900 min False
  960 min True
  ```
  The token is still valid at 16 minutes, at 60 minutes, and at 14 hours 59 minutes. It only expires after 900 minutes, which is 15 hours.
- **Why it matters:** The changelog tells readers that a stolen or leaked reset link is only useful for 15 minutes. In fact it is useful for 60 times longer. This is a security feature, so the gap is the one thing it exists to prevent. If it shipped, users and auditors would believe they had a 15-minute window and would have a 15-hour one.
- **Suggested fix:** In `is_expired`, compare against `TOKEN_TTL` and drop the `* 60`: `return now - token.created_at > TOKEN_TTL`. `TOKEN_TTL` is already in seconds, as its comment says.

## Finding 2: Gap (the tests cannot detect this bug, so "Covered by tests" overreaches)

- **Claim as stated:** "Covered by `tests/test_auth.py`."
- **What I ran:** `python -m pytest -q tests` gave `2 passed`. They pass against the buggy code.
- **Why:** `test_fresh_token_is_valid` checks age 60 seconds, which passes under both 15 minutes and 15 hours. `test_old_token_is_rejected` checks age 2 days, which also fails validation under both. Neither test has an age between 15 minutes and 15 hours, which is exactly where the bug lives. The tests show that tokens are not valid forever and that they are valid when brand new. They do not test the 15-minute boundary.
- **Test that would close it:** add boundary tests, for example:
  - age 899 s: not expired, and redeem returns the user id
  - age 901 s: expired, and redeem raises `PermissionError`
  - age 1 hour: expired

  I have not run these against a fixed version, since I may not modify the project. I expect the 901 s and 1 hour cases to fail today and all of them to pass after the fix. If you add them, run them both before and after the fix, so you know the new tests really do fail on the bug.

## What held up

- `TOKEN_TTL` itself is correct: 15 * 60 = 900 seconds, and the comment matches. I confirmed this by printing it.
- `redeem` correctly raises `PermissionError` when `is_expired` is true, and returns `user_id` otherwise. This is read from the code, and the two existing tests exercise both branches.
- Tokens come from `secrets.token_urlsafe(32)`, which is a sound choice for reset tokens. I read this and did not test it. It is outside the 3.2.0 claim, so this is only a note.
- The two existing tests pass (I ran them), and they are fine as far as they go. They just do not reach the boundary.
- I did not examine anything beyond these files. There is no code here for sending the email, storing tokens, or single use, so I make no statement about those parts.

## Verdicts

- "Password reset tokens now expire after 15 minutes": **Unsupported.** The effective lifetime is 54000 seconds (15 hours). After the one-token fix, the claim becomes true, and I would then expect it to be supported once the boundary tests pass.
- "Covered by `tests/test_auth.py`": **Supported, narrower.** What the evidence supports is: "`tests/test_auth.py` checks that a fresh token is accepted and a 2-day-old token is rejected." It does not cover the 15-minute limit, and it passes with the bug in place.
