Hi, and thanks for the kind words. First security feature is a big deal, and I'm glad to look at this before your lead does. The short version: the changelog entry is not true yet, and the bug is a one-line fix. Verdict below, then details.

**Verdict: Contradicted.** The 3.2.0 entry says password reset tokens expire after 15 minutes. In the current code they expire after 15 hours.

**The bug**

`auth.py`, line 5 defines `TOKEN_TTL = 15 * 60`, which is already in seconds (900). Line 17 then does:

    return now - token.created_at > TOKEN_TTL * 60

so the effective limit is 900 * 60 = 54,000 seconds, or 15 hours. I confirmed this by running the module from a scratch copy (not your run folder):

- Token age 901 s (15.0 min): not expired. Should be expired.
- Token age 53,999 s (899.98 min): not expired.
- Token age 54,001 s (900.02 min): expired.

So the boundary is at 15 hours, which contradicts the changelog.

**Why the test does not catch it**

`tests/test_auth.py::test_old_token_is_rejected` checks a token that is two days old. That is well past both 15 minutes and 15 hours, so it passes under the bug. I ran `pytest tests/test_auth.py`: 2 passed. I also made the fix in the scratch copy (`TOKEN_TTL * 60` changed to `TOKEN_TTL`) and reran: still 2 passed. A test that passes with the bug present and with the bug fixed is not evidence for the claim. The changelog's "Covered by `tests/test_auth.py`" is therefore misleading as written.

**What would settle it**

Add a test that sits on the 15-minute boundary, for example:

- A token created at t, checked at t + 14 min: valid.
- The same token checked at t + 16 min: rejected with `PermissionError`.

Run it against the current code first. It should fail, because the 16-minute token is accepted. Then apply the one-line fix (line 17 becomes `> TOKEN_TTL`) and confirm it passes. Only then does "Covered by tests" mean something.

**Suggested changes**

1. Fix line 17 as above.
2. Add the boundary test, and confirm it fails before the fix and passes after.
3. Keep the changelog line, since it will then be true. If you want to be careful about scope, you could also say which path enforces the expiry (see below).

**What I did not examine**

- Nothing outside `auth.py` and `tests/test_auth.py` was in the run folder. I did not check where tokens are issued, whether `redeem` is actually called in the reset flow, whether tokens are single-use, or how they are stored. The changelog claims a feature that depends on that code, and I could not see it.
- I did not check the `now` parameter path in production, only the explicit `now=` values in my probes.
