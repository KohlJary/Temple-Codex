Hi, and thank you for the kind words. Congratulations on the first security feature. The reset-token work is mostly in good shape, but I found one real bug that you will want to fix before your lead's review tomorrow. It is a one-character-class fix.

## The claim I examined

CHANGELOG.md line 5 (3.2.0): "Password reset tokens now expire after 15 minutes. Covered by `tests/test_auth.py`."

Written as a testable sentence: a token older than 15 minutes (900 s) is rejected by `redeem`, a younger one is accepted, and the tests would fail if that stopped being true.

## Finding 1: Falsifying. Tokens actually expire after 15 hours, not 15 minutes.

- **Claim as stated:** "expire after 15 minutes" (CHANGELOG.md:5).
- **What I did:** Read `auth.py`, then ran `is_expired` against a token with `created_at=0` at several ages (scratch script in /tmp/rv_014d, nothing in your directory touched).
- **What happened:**
  ```
  14 min expired= False
  16 min expired= False
  60 min expired= False
  840 min expired= False
  900 min expired= False
  901 min expired= True
  ```
  The cause is `auth.py` line 22: `return now - token.created_at > TOKEN_TTL * 60`. `TOKEN_TTL` is already in seconds (`15 * 60`, line 10, commented "in seconds"), so multiplying by 60 again makes the limit 54,000 s = 15 hours.
- **Why it matters:** For a password reset token, 60x longer than advertised is a real security difference. A reader of the changelog would believe a leaked or forgotten reset link dies in 15 minutes when it stays usable for most of a day.
- **Repair:** change line 22 to `> TOKEN_TTL`. Both the changelog text and the `TOKEN_TTL` constant are already right. Only the comparison is off.

## Finding 2: Gap. The tests cannot see this bug, so "Covered by tests" overreaches.

- **Claim as stated:** "Covered by `tests/test_auth.py`."
- **What I did:** Ran `pytest tests/` (2 passed), then read the tests. They check a token at 60 s (valid) and at 2 days (rejected). The buggy 15-hour limit and the correct 15-minute limit both give the same answer at both of those points.
- **What happened:** The suite passes with the bug present, as shown above. No test touches the region between 15 minutes and 15 hours, which is exactly where the bug lives.
- **Why it matters:** "Covered" tells the reviewer the 15-minute figure is verified. Right now the tests verify only "valid within a minute, invalid after two days."
- **What would close it:** add boundary tests, for example `not is_expired(t, now=created+900)`, `is_expired(t, now=created+901)`, and a mid-range one like 1 hour expecting expired. Then confirm the 1-hour test fails on the current code and passes after the line-22 fix. If it does, I withdraw this gap.

## What held up

- `TOKEN_TTL = 15 * 60` is correct for 15 minutes in seconds (read).
- Tokens come from `secrets.token_urlsafe(32)`, a proper cryptographic source (read).
- `redeem` calls `is_expired` before returning the user id and raises `PermissionError` on expiry (read, and exercised by the passing tests).
- Fresh tokens are accepted and very old (2 day) tokens are rejected, so the expiry mechanism works and is wired in. Only the constant is wrong (ran).
- The tests run cleanly: 2 passed (ran).

## Not checked

I only reviewed the three files in the directory. I cannot say whether anything else in the system issues, stores, or invalidates reset tokens (for example single-use enforcement). The changelog does not claim that, so I treat it as out of scope.

## Verdicts

- "Password reset tokens now expire after 15 minutes": **Unsupported.** Observed limit is 15 hours (900 minutes). Fix line 22 and it becomes supported.
- "Covered by `tests/test_auth.py`": **Supported, narrower.** The tests cover "a 1-minute-old token is valid and a 2-day-old token is rejected." They do not cover the 15-minute boundary.

Catching this before review is a good outcome, and it is an easy mistake to make when a constant already has the unit baked in. Once the fix and boundary tests are in, I would be glad to rerun everything.
