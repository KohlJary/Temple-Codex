Hi! Good news first: the structure here is clean and the bug is a one-line fix, so you have plenty of time before tomorrow's review. But the 3.2.0 claim is not true of the code as it stands, and I'd want you to know before your lead does.

## Claim, narrowed

CHANGELOG.md, 3.2.0: "Password reset tokens now expire after 15 minutes. Covered by `tests/test_auth.py`."

As a testable sentence: a reset token older than 15 minutes is rejected by `redeem()`, and the tests would fail if that were not so.

## Finding 1: Falsifying. Tokens actually live 15 hours.

- **Claim as stated:** "expire after 15 minutes" (CHANGELOG.md, 3.2.0).
- **What I did:** Read auth.py, then copied the project to /tmp/rv_e900/w (I did not touch your directory) and called `is_expired` on a token created at t=0 at several ages.
- **What happened:**
  - `auth.py:5` has `TOKEN_TTL = 15 * 60  # 15 minutes, in seconds`, which is already 900 seconds.
  - `auth.py:17` has `return now - token.created_at > TOKEN_TTL * 60`, which multiplies by 60 again, giving 54,000 seconds.
  - Output of my run:
    ```
    16 min expired: False
    60 min expired: False
    900 min expired: False
    901 min expired: True
    15.0 hours
    ```
- **Why it matters:** A reset token is a bearer credential for account takeover. This feature exists to shrink the window in which a leaked link works, and the window is 60x wider than the changelog says. Anyone reading the changelog (including a security reviewer) would believe a stale link is dead after a quarter of an hour, and it is not.

**Repair:** drop the extra factor on line 17: `return now - token.created_at > TOKEN_TTL`. (I did not apply this; the file is yours.)

## Finding 2: Falsifying (the "Covered by" half). The tests cannot detect this bug.

- **Claim as stated:** "Covered by `tests/test_auth.py`."
- **What I did:** Read both tests and ran `pytest` on my copy.
- **What happened:** `2 passed`. The tests check a token at +60 seconds (valid) and at +2 days (expired). Both pass with the 15-hour bug, and would also pass with a 1-hour or 1-day TTL. Nothing exercises the 15-minute boundary, so the coverage claim is untrue as to the 15-minute behavior.
- **Why it matters:** A green suite here gives false assurance. It is the reason the bug went unseen.
- **What would close it:** add boundary tests, for example `now = created_at + 15*60` is still valid (or is expired, whichever you decide, but pin it down), `+ 15*60 + 1` is expired, and `+ 16*60` is expired. After the one-line fix, the 16-minute test passes. Before the fix it fails, which is the check that it really tests the claim. I did not run the tests with the fix applied; I only observed that the current code gives `False` at 16 minutes.

## What held up

- `TOKEN_TTL = 15 * 60` is the correct value for 15 minutes in seconds (read; confirmed 900).
- `redeem()` does raise `PermissionError` when `is_expired` is true, and returns `user_id` otherwise (read, and exercised by both existing tests).
- Tokens come from `secrets.token_urlsafe(32)`, a suitable generator for this purpose (read only; I did not review the rest of the reset flow, which is not in this directory).
- The existing tests pass (ran: 2 passed) and do what they say: fresh is valid, two days old is rejected.

## Not examined

Only auth.py, the tests and the changelog exist in this directory. I could not check that the reset flow actually calls `redeem()`, that tokens are single-use, or how `created_at` is stored. The changelog does not claim those things, so I have not marked them as gaps.

## Verdicts

- "Password reset tokens now expire after 15 minutes": **Unsupported.** Observed expiry is at 15 hours.
- "Covered by `tests/test_auth.py`": **Unsupported.** The tests pass regardless of whether the TTL is 15 minutes or 15 hours.

You can say it directly to your lead: you caught a unit mix-up (seconds multiplied by 60) before release, and the fix is one line plus a boundary test. That is a good outcome for a first security feature. I hope the review goes well tomorrow.
