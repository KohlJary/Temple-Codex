**Claim as stated (NOTES.md, line 3):** "adding the retry in `retry.diff` fixes the flakiness in test_upload_large."

## Verdict on the claim

**Supported, narrower.** The retry makes test_upload_large pass 200/200 on this setup where the unchanged commit passes 183/200. It does not show that the cause of the flakiness is fixed. The retry absorbs connection resets; it does not explain them.

Suggested sentence: "On commit a1b2c3d, adding a bounded retry (3 attempts, on requests ConnectionError) took test_upload_large from 183/200 to 200/200 passes on one machine, and every failure before the change was a connection reset inside upload_chunk."

## What I did

- Read NOTES.md, retry.diff, runs/before.txt, runs/after.txt.
- Checked the log arithmetic and the run numbering with grep and awk. Before: 183 passed, 17 failed, 17 distinct run numbers (max 198). After: 200 passed, 0 failed.
- Ran an exact two-sided Fisher test on 17/200 vs 0/200 (scipy).
- Wrote a standalone copy of the new `upload_chunk` from the diff's "+" side and ran it under pytest with fake sessions (scratch file /tmp/rv_7ea6/test_retry.py). I did not have the repo, so I did not run test_upload_large itself and did not rerun any batch.

## What held up

- **The counts are internally consistent.** Both log headers total 200 runs. Every failure line is a `ConnectionResetError(104)`, and the 17 failing runs are distinct.
- **Interleaving is recorded in the logs.** before.txt and after.txt both say "10 batches of 20 interleaved," which is the control the NOTES describes.
- **The difference is not chance.** Exact two-sided Fisher p is about 1.1e-5 for 17/200 vs 0/200. The 95% upper bound on the after-rate is about 1.8%.
- **The retry log agrees with the failure log.** 19 of 200 runs (9.5%) triggered a retry, against 17 of 200 (8.5%) failing before. The totals also add up: 18 runs with one retry and 1 run with two is 20 retries across 19 runs. This is the pattern you would expect if the retry is catching the same resets.
- **The retry logic does what the diff says** (scratch tests, 4 passed):
  - Two resets then success: 3 calls, sleeps of 0.5 s then 1.0 s.
  - Three resets: raises after 3 calls.
  - HTTP 500: not retried.
  - ReadTimeout: not retried.

## Findings

**1. Overreaching: "fixes the flakiness."** The data supports "passes 200/200 here with the retry, vs 183/200 without." It does not show why the resets happen. A retry that hides a server-side or network fault would look exactly like this in the logs. Repair: use the suggested sentence above.
- Claim as stated: NOTES.md line 3.
- What I did: read the claim against the logs and the diff.
- What happened: before.txt has 17 connection-reset failures; after.txt has none; neither log says anything about cause.
- Why it matters: a reader would think the bug is fixed in the uploader or the network, when the retry only masks it.

**2. Gap: the traceback line does not match the diff.** Every failure is logged at `uploader/client.py:15 upload_chunk`. In the original file, retry.diff's hunk `@@ -12,5` maps old line 12 to blank, 13 to `def upload_chunk`, 14 to `resp = self.session.put(...)`, 15 to `resp.raise_for_status()`, and 16 to `return resp`. A ConnectionError cannot come from `raise_for_status()`, so the log's line number either comes from a different version of the file or is off by one.
- What it does not change: the count of failures or the fact that they are in upload_chunk.
- Test that closes it: `git show a1b2c3d:uploader/client.py | sed -n 12,16p`. If line 15 is not the put call, correct the log or explain the offset.

**3. Note: the NOTES wording conflicts with the logs.** NOTES says "200x on commit a1b2c3d without the change, then 200x with ONLY retry.diff applied ... alternated batches of 20." "Then" describes sequential runs; the logs say interleaved. The interleaving is the control against "quiet network time," so the method description should match what was actually done. Fix: change NOTES to say the batches were interleaved, as the log headers state.

**4. Gap: the retry counts come from a build that is not clearly the one that passed.** after.txt says the retry numbers came from "added debug counter, removed before commit." It is not stated whether those 19 retry runs are the same 200 runs whose result is 200/200, or from a separate instrumented run.
- Test that closes it: rerun the final diff for 200 iterations with the counter on and off, and log retries per run alongside pass/fail.

**5. Gap: the test's correctness under retry is not checked.** The retry re-sends the full 8 MB chunk after a reset. That is safe only if the server treats PUT as idempotent, and if a reset after a committed write does not corrupt the upload. Neither the logs nor the test say whether the final object was verified.
- Test that closes it: check the server's PUT handler for idempotency, or add a checksum assertion to test_upload_large and rerun before/after.

**6. Gap: the environment is not recorded.** NOTES says "same machine, same afternoon," but neither log has a host, a timestamp, or a kernel/network setting. The effect is clear on this machine, but I cannot say it holds elsewhere.
- Test that closes it: rerun the before/after pair on a second machine, or at a different time of day, and record hostname and timestamps in the log headers.

**7. Note: ReadTimeout is not retried.** `requests.exceptions.ReadTimeout` is a Timeout, not a ConnectionError, so the retry does not cover it (confirmed in the scratch test). No timeouts appear in the logs, so this does not affect the claim. It matters if slow uploads start failing in production. Only raise this if you want the retry to cover them.
